Decisione architetturaleIl MCP Server non è un runtime agentico, un LLM proxy o un generatore di SQL. È il capability boundary OUF per agent e client MCP esterni: espone strumenti tipizzati, applica manifest, authorization context, validation, orchestration budget e audit, e prepara esclusivamente l’handoff delle ApprovalChallenge verso il Trusted Approval Workspace della Trusted Human Surface (THS). Modello, prompt, memoria, analisi e fonti ulteriori appartengono al client esterno. La THS è un trust boundary umano separato: il MCP non ospita la UI fiduciaria, non esegue Protected Human Operations e non riceve i dati protetti visualizzati nella THS.
Executive delta v1.4 — Operational Awareness via MCP
La v1.4 estende il ruolo del MCP Server senza modificarne il security boundary: oltre alla typed capability exposure, il MCP costituisce la superficie conversazionale governata con cui un utente autorizzato può interrogare lo stato operativo OUF e ricostruire fault, retry, recovery e incidenti avvenuti mentre il client/chatbot non era connesso. La sorgente di verità resta nei moduli owner; il MCP non diventa un sistema di monitoring né un repository centralizzato di log. La persistenza e il catch-up sono obbligatori; le notifiche live sono opzionali e non possono essere l’unica evidence di un evento.
0. Executive Summary
Il modulo OUF MCP Server costituisce la superficie governata con cui agent e client MCP esterni accedono alle capability dell’Open Urban Framework. Non interpreta il linguaggio naturale e non ospita modelli: riceve chiamate MCP strutturate, le valida, le autorizza e le instrada verso capability OUF tipizzate, mantenendo separati client agentico, query planning, persistenza, object resolution e decisioni autoritative. La Trusted Human Surface (THS) è invece la superficie web OUF-controlled per interazioni HUMAN_USER che non devono transitare nel canale MCP; il Trusted Approval Workspace è il bounded context THS dedicato alle decisioni autoritative.
• Nessun SQL/JPQL/Criteria/Cypher/SPARQL/CTE o predicato arbitrario generato dall'Agent.
• Tool specialistici con DTO fortemente tipizzati e Capability Manifest machine-readable + human-readable.
• Authorization server-side e DataAccessLabel enforcement prima che i dati OUF siano restituiti al client esterno.
• Query Complexity Governor nel servizio UDP, distinto dall'Agent Orchestration Budget del MCP.
• Human-in-the-loop obbligatorio per merge/split confirm, authority override, onboarding approve/activate e azioni equivalenti, eseguito nel Trusted Approval Workspace della Trusted Human Surface.
• Errori machine-readable preservati; mismatch di capability produce remediation esplicita, non redirect automatico.
• Retry-loop guard e cumulative budget impediscono loop agentici, fan-out eccessivo e consumo non bounded.
• MCP non introduce broker, Redis, graph DB, vector DB o service mesh nella baseline.
Executive Freeze targetLa v1.2 introduce la baseline Go approvata dal Technology Economy Gate e conserva senza modifiche il contratto MCP, l’allineamento alla Trusted Human Surface v1.4 e le architetture funzionali già congelate.
1. Scopo, perimetro e non-obiettivi
Il modulo espone capability OUF a client conversazionali e agentici esterni. Riceve invocazioni MCP strutturate già formulate dal client, le valida e le orchestra verso strumenti deterministici e autorizzati. Non interpreta richieste in linguaggio naturale e non diventa system of record di dati urbani, semantic registry, IAM, ETL runtime o query engine.

1.1 Principi normativi
• Capability before invocation: l’agent esterno può chiamare soltanto strumenti pubblicati e versionati.
• Server-side enforcement: agent, modello e client non sono security boundary OUF.
• Typed inputs, bounded outputs: nessun tool accetta SQL, codice eseguibile o filtri arbitrari.
• Explainable orchestration: decisione del tool, parametri, errori e remediation sono auditabili.
• Human authority: il client/Agent esterno non può trasformare consenso testuale in commit autoritativo; la decisione HUMAN_USER avviene nel Trusted Approval Workspace della THS.
• Fail closed: ambiguity, stale approval, missing policy context o security error non degradano in ALLOW.

Urban API Gateway resta il boundary di rete e coarse authorization sia sul percorso northbound client→MCP sia sul percorso MCP→capability owner; la duplicazione nel diagramma rappresenta due passaggi logici dello stesso componente. Authorization & Access Control resta owner delle policy. UDP resta owner di query governance, materializzazione e Object Resolution. MCP governa le sole chiamate OUF e non assorbe le capacità analitiche del client esterno.
2.1 Gateway-mediated execution path
Tutte le invocazioni originate dal MCP verso capability OUF seguono il binding governato dal Gateway. Il MCP non possiede shortcut agentici diretti verso UDP, Onboarding, Ingestion, Semantic Registry, Data Lake o verticali.
External AI Agent / MCP Client    |    vUrban API Gateway — northbound    |    vOUF MCP Server    |    vUrban API Gateway — capability binding    |    +-----------+-----------+-----------+-----------+    v           v           v           v   UDP      Onboarding   Ingestion    Semantic Registry    |    vfine-grained authorization / query governance / domain execution
GWMCP-01 — Un capability handler MCP risolve capabilityId e logical binding; non costruisce URL backend arbitrari. Endpoint fisici e route sono risolti da configurazione/registry governati.
GWMCP-02 — Eventuali chiamate service-to-service non HTTP formalmente previste dalla piattaforma devono comunque usare workload identity e contratti governati; non costituiscono un bypass della capability policy.

10. Trusted Human Surface e Trusted Approval Workspace
External AI Agent / MCP Client -> proposal      -> plan / impact      -> create/link ApprovalChallenge      -> return trustedApprovalRefOUF Trusted Human Surface  -> Trusted Approval Workspace [OUF-controlled]      [HUMAN_USER sees exact diff/hash/version]      -> HUMAN confirms      -> direct user-bound call via Gateway      -> backend revalidates hash/ETag/state/policy      -> commitProtected Operations Workspace [THS]      -> HUMAN_USER-only protected operations      -> never invoked or rendered through MCP      -> no protected log payload returned to external AI/MCP
• Testo o messaggio del client che dichiara «l’utente approva» non vale come approvazione.
• Challenge one-time, expiring, bound a actor/session/target hash.
• Commit revalida resource version e authorization.
• Audit separa proposta, decisione umana e scadenza automatica: EXPIRED non richiede human actor; APPROVED, REJECTED e REVOKED richiedono prova e attore umano verificabili.
10.1 Authoritative action path
Le capability TRUSTED_HUMAN_ONLY non vengono invocate dal ToolRouter. Il client/Agent esterno prepara proposta, diff, impact e challenge reference; il Trusted Approval Workspace, bounded context della Trusted Human Surface OUF-controlled, esegue quindi una chiamata autenticata user-bound direttamente verso Gateway e backend owner. Il MCP non ospita la THS e non accede al Protected Operations Workspace.
External AI Agent / MCP Client  -> plan / explain / propose  -> create or link ApprovalChallenge  -> return trustedApprovalRefTrusted Human Surface [OUF-controlled]  -> Trusted Approval Workspace      -> HUMAN_USER sees exact diff/hash/version      -> direct authenticated request      -> Urban API Gateway      -> backend owner      -> revalidate actor + hash/ETag/state/policy      -> commit authoritative action  -> Protected Operations Workspace      -> out of MCP scope; HUMAN_USER-only
HUMAN-01 — Nessun pulsante Approva/Conferma del Trusted Approval Workspace della THS chiama un tool MCP di conferma.
HUMAN-02 — Il MCP non detiene né riutilizza token umani privilegiati per completare la decisione.
HUMAN-03 — L'audit conserva delegatedVia=AI_AGENT/MCP_SERVER per la proposta e actor=HUMAN_USER per la conferma, senza impersonazione.

• TTL/cleanup governati.
• Fail-closed o fail-bounded su contention/timeout.
• Redis entra solo con misure che dimostrino necessità.

14. Retry-loop guard
• Ogni tentativo riceve semanticAttemptFingerprint versionato.
• Il fingerprint non contiene testo conversazionale: usa toolName, argomenti normalizzati e hash/HMAC.
• Modifiche cosmetiche del DTO non resettano il contatore.
• Tentativi semanticamente equivalenti oltre soglia -> TOOL_SELECTION_STALLED.
• Il contatore è budget-window-scoped e condiviso multi-Pod; sessione, reconnect e correlation_id non lo azzerano.
attempt 1 -> mismatchattempt 2 -> same semantic fingerprintattempt 3 -> cosmetic DTO changes, same intentthreshold reached -> TOOL_SELECTION_STALLED

23.1 Evidence Ingress Path
Responsabilità. L’alimentazione di ouf_mcp.owner_evidence_inbox è responsabilità esclusiva dell’Evidence Ingress Adapter, funzione stateless del perimetro di integrazione già esistente dell’Urban API Gateway. Non è un runtime agentico, un servizio crittografico, un nuovo deployable del modulo MCP o una modifica alla topologia descritta nei §§65 e 85. Gateway, servizio di identità dell’Ente e Adapter costituiscono la Trusted Computing Base (TCB) del solo percorso di ingresso. Il ruolo PostgreSQL ouf_mcp_evidence_ingress_role è assegnato esclusivamente alla workload identity dell’Adapter; mcp-server e i client agentici esterni non possono alimentare la inbox.
Flusso bounded. Il backend owner invia l’evidenza attraverso l’Urban API Gateway usando l’identità M2M EXTERNAL_SYSTEM già prevista: OAuth2 client credentials oppure mTLS, secondo la configurazione vigente di Gateway e Authorization/IAM. Il Gateway valida canale, token e contesto di autenticazione e propaga all’Adapter il service principal attendibile. L’Adapter deriva backend_owner dall’identità propagata, usa l’eventuale owner nel payload soltanto per rilevare incoerenze, associa backend_request_id all’attempt autoritativo, valida lo schema, canonicalizza il payload e calcola evidence_payload_hash. Nessun identificativo di owner o principal fornito nel body è usato come autorità.
Esiti. Credenziali M2M invalide o scadute, contesto di identità attendibile assente, owner incoerente o backend_request_id non associabile producono un rifiuto strutturato; quando applicabile il Gateway risponde HTTP 401/403, l’evento è inviato al SIEM e la inbox resta invariata. Con identità valida e binding coerente, l’Adapter inserisce una sola riga in stato VERIFIED, dove VERIFIED significa ammessa dal percorso autenticato e validata per schema e binding, non firma applicativa o non-ripudio. verified_by contiene il service principal M2M derivato dal trusted identity context e verified_at il timestamp di ammissione. Solo allora evidence_ref può essere usato dal percorso di late recovery.
Idempotenza semantica. UNIQUE(backend_owner, backend_request_id) è il gate di collisione, ma l’esito dipende anche da evidence_payload_hash: stessa chiave e stesso hash producono replay idempotente, stessa evidence_ref e nessun duplicato; stessa chiave e hash diverso producono EVIDENCE_INGRESS_CONFLICT, lasciano invariata la riga originaria e generano un security event. Il ruolo ingress dispone, oltre all’INSERT già segregato, del solo SELECT colonnare su evidence_ref, backend_owner, backend_request_id ed evidence_payload_hash necessario a classificare collisione, replay e conflitto; non possiede UPDATE, DELETE o TRUNCATE. La stored procedure di §75 continua, come difesa indipendente, a verificare scope e binding attempt/window/owner/backend_request_id prima di applicare qualsiasi compensazione.
Confine dichiarato. La baseline v1.0 usa il canale protetto e l’identità workload autenticata già offerti da Gateway e Authorization/IAM; non introduce firme detached JWS/HMAC sulle evidence, trust store dedicati, key ring, rotazioni o revoche crittografiche nel modulo MCP. I moduli Authorization/IAM v1.4 e Urban API Gateway v1.2 restano frozen e non ricevono nuovi requisiti. Un’eventuale esigenza futura di non-ripudio dell’evidence richiederà un requisito cross-module separato, versionato e approvato; non è prerequisito dell’Executive Freeze v1.0.

68. Pipeline concreta di invocazione tool
McpToolEndpoint.call(toolName, rawArguments)  1. validate MCP 2026-07-28 headers and required per-request _meta  2. authenticate service principal; resolve optional OUF application session  3. pin one immutable ManifestSnapshot for the request/turn  4. resolve toolName → capabilityId/owner/operationClass/gatewayBindingRef  5. validate eligibility, visibility, typed DTO and coarse authorization  6. resolve canonical budget_window via server-side get-or-create  7. derive rotation-compatible fingerprints and stable equivalence_group_id  8. AttemptAdmissionService.reserve(): idempotency + retry + budget + attempt + reservation atomici  9. mark dispatch state; call Gateway with scoped idempotency key/request hash 10. backend re-authorizes fine-grained data and returns backend request/result reference 11. enforce streaming byte/object caps before external client delivery 12. reconcile reservation and attempt idempotently; stale dispatch → UNKNOWN and maintenance recovery 13. append immutable audit references and return MCP result
I passaggi 1-8 precedono qualsiasi backend call. AttemptAdmissionService è l’unico owner della transazione di ammissione. Nessuna transazione DB resta aperta durante I/O. UNKNOWN blocca retry non idempotenti finché il backend owner non consente una reconciliation deterministica.
69. Capability Registry implementation
Il Capability Registry carica manifest versionati inclusi nell’artifact/configuration bundle. Ogni richiesta o turn acquisisce un ManifestSnapshot immutabile identificato da version e checksum; il refresh pubblica atomicamente il nuovo snapshot, ma non cambia quello già pin-nato. Gli snapshot ancora referenziati da sessioni, attempt o audit restano risolvibili per l’intera retention applicabile. Il created_manifest_checksum della sessione è solo il default iniziale; manifest_checksum sul tool_attempt è il riferimento autoritativo dell’esecuzione.

79. RetryLoopGuard — canonical fingerprint
Il fingerprint deve rappresentare l'intento tecnico del tentativo, non la formulazione testuale.
CanonicalAttemptMaterial = {  canonicalCapabilityId, capabilityMajorVersion, operationClass,  normalizedLogicalTarget, normalizedPredicates(sorted), normalizedSpatialIntent,  normalizedTemporalIntent, requestedProjection(sorted),  userGoalClass  // enum server-side versionato, mai testo libero o label prodotta dal modello}canonicalIdentityHash = SHA256(canonicalJson(nonSensitiveMaterial))groupHash[v] = "v"+v+":hmac-sha256:"+BASE64URL(HMAC_SHA256(groupKey[v], canonicalJson(material)))fingerprint[v] = "v"+v+":hmac-sha256:"+BASE64URL(HMAC_SHA256(fingerprintKey[v], canonicalJson(material)))canonicalIdentityHash è solo una chiave di unicità tecnica e non include valori personali/sensibili; se il target non può essere rappresentato senza tali valori si usa un opaque stable target ref già pseudonimizzato. La UNIQUE impedisce gruppi duplicati tra Pod. Gli alias HMAC corrente/precedente sono inseriti atomicamente e devono convergere sul medesimo equivalence_group_id. Le versioni restano pin-nate per budget_window fino alla fine della retention. L'envelope è algorithm-aware: version:algorithm:digest. L'allowlist DB iniziale ammette hmac-sha256 e hmac-sha384; ogni evoluzione usa expand/contract: DDL N+1 prima dei Pod N+1, coesistenza mixed-version testata, ritiro di N soltanto dopo fine retention e riferimenti.
• Nessun testo conversazionale grezzo.
• No access token, subject claim o sensitive value se non indispensabile; preferire stable opaque refs.
• Ordine delle liste semanticamente unordered canonizzato.
• Campi cosmetici/client-generated ignorati.
• fingerprintVersion persistito per future migration.
80. RetryLoopGuard algorithm
RetryLoopGuard usa blocking_attempts, non un booleano. total_attempts classifica la prima chiamata; is_equivalent_retry è persistito sull'attempt e governa active/equivalent_retry_attempts. UNKNOWN incrementa blocking_attempts una sola volta. Una prova owner autoritativa lo decrementa una sola volta; UNRESOLVED lo mantiene. Nessun amministratore può azzerare il contatore assumendo l'assenza di side effect.
Una capability canonica realmente diversa può appartenere a un altro gruppo; whitespace, ordine, alias mappato, rotazione HMAC, sessione, reconnect o correlation_id non cambiano equivalence_group_id. MCP possiede il conteggio agentico; UDP produce mismatch/budgetImpact senza mantenere retry state.

122. Executive Alignment v1.2 — Trusted Human Surface / Trusted Approval Surface
La v1.2 conserva l’allineamento del modulo MCP Server alla Trusted Human Surface (THS) definita nel Source Onboarding, Configuration & Authorization v1.4. La THS è un modulo logico comune OUF co-locato fisicamente nel deployable del control plane. Il Trusted Approval Workspace resta il bounded context della THS dedicato alle decisioni HUMAN_USER autoritative. Il MCP Server resta un deployable distinto e non ospita né renderizza la THS.
122.1 Confine MCP ↔ Trusted Human Surface
• MCP-THS-01 — Il MCP può preparare una proposta, creare o linkare una ApprovalChallenge e restituire un trustedApprovalRef opaco. Il riferimento non è una bearer credential e non trasferisce autorità HUMAN_USER.
• MCP-THS-02 — La conferma avviene esclusivamente nel Trusted Approval Workspace della THS con sessione HUMAN_USER e chiamata diretta via Urban API Gateway al backend owner. Nessun confirm/approve/activate/publish passa da tools/call.
• MCP-THS-03 — Il MCP non possiede, persiste o riutilizza token umani privilegiati e non riceve il payload della decisione oltre ai riferimenti/audit minimizzati necessari alla correlazione.
• MCP-THS-04 — Il Protected Operations Workspace della THS è fuori dal perimetro MCP. Le operazioni di ricerca, lettura, filtro, aggregazione deterministica, correlazione tecnica, export e download dei log protetti sono Protected Human Operations, non capability OUF/MCP.
• MCP-THS-05 — Le Protected Human Operations non sono discoverable tramite tools/list, resources o prompts, non possono essere sintetizzate come tool dal client e non sono raggiungibili da binding MCP verso Gateway/backend.
• MCP-THS-06 — I log di sistema contenenti dati personali (inclusi nome, cognome, codice fiscale e identificativi equivalenti) non vengono restituiti al client AI/MCP. L’eventuale accesso avviene esclusivamente nella THS con HUMAN_USER autorizzato.
• MCP-THS-07 — OUF non introduce un Agent AI interno. Qualunque interpretazione AI resta responsabilità del client esterno e non modifica il divieto di accesso MCP ai dati protetti della THS.
122.2 Interazione consentita

33. Operational Awareness Plane — chatbot come superficie operativa governata
33.1 Requisito di prodotto e confine
OUF non assume una console amministrativa dedicata come prerequisito della baseline. Quando il chatbot/MCP client costituisce l’unica superficie utente disponibile, il MCP Server DEVE consentire a un utente autorizzato di conoscere lo stato corrente della piattaforma e gli eventi operativi significativi avvenuti nel passato, inclusi quelli prodotti durante periodi di disconnessione del client.
MCP non sostituisce Prometheus, logging, tracing o strumenti SRE: espone una proiezione semantica, bounded e autorizzata dello stato operativo.
Nessun raw log stream, query SQL, PromQL arbitrario, Kubernetes API o endpoint diagnostico non governato è esposto come tool MCP.
Il modello è pull/catch-up first: un evento significativo deve restare interrogabile dopo la disconnessione del chatbot. Eventuali notification MCP/live sono best-effort e non costituiscono source of truth.
Nessun nuovo deployable centrale per gli incidenti è richiesto nella baseline: ogni modulo persiste gli eventi di propria ownership nel datastore già adottato e li rende disponibili tramite contratti/capability governate.

33.3 Operational Event projection contract
Il MCP DEVE consumare e proiettare un contratto normalizzato con almeno i seguenti campi. I producer possono avere campi domain-specific additivi, ma non possono omettere quelli required quando applicabili.
OperationalEvent { eventId, incidentId?, module, eventType, lifecycleState, severity, firstSeenAt, lastSeenAt, resolvedAt?, correlationId?, sourceRef?, jobRef?, errorCode?, retryState?, nextRetryAt?, impactSummary, actionRequired, evidenceRefs[], dedupKey, tenantScope, visibilityClass }
lifecycleState ∈ {OPEN, RECOVERING, RESOLVED}; severity ∈ {INFO, WARNING, ERROR, CRITICAL}.
eventType e errorCode devono essere machine-readable e stabili; impactSummary è una sintesi safe-for-user e non può contenere secret o payload personali non autorizzati.
dedupKey deve consentire aggregazione di eventi ripetitivi nello stesso incidente; retry tecnici ripetuti non devono diventare automaticamente N incidenti distinti.
actionRequired distingue incidente informativo/auto-risolto da condizione che richiede intervento umano.
evidenceRefs devono referenziare evidence governata; il MCP non dereferenzia evidence protetta senza Authorization.
33.4 Catch-up, cursor e reconnect
Le capability summary/history DEVONO accettare una finestra temporale o cursor opaco. Il server non dipende dalla memoria del chatbot per ricostruire il passato.
Un client può conservare lastSeen cursor, ma l’assenza di cursor non impedisce una query bounded per intervallo.
Al reconnect il MCP non deve fingere push affidabile: il chatbot può eseguire un lightweight status/summary check, ma tale comportamento è una policy client e non un requisito di disponibilità del protocollo.
Un evento RESOLVED resta interrogabile per la retention definita dal producer/PET; non scompare immediatamente alla recovery.
33.5 Authorization e redaction
Ogni query operational-awareness richiede principal context verificato e capability authorization dedicata.
Tenant/source/module visibility è applicata server-side; il modello/chatbot non è un security boundary.
Security incident, dati personali, hostname sensibili, token, secretRef e stack trace non possono essere restituiti salvo capability specifica e policy esplicita; i secret non vengono mai restituiti.
Il risultato deve distinguere NOT_AUTHORIZED da NO_INCIDENTS per evitare conclusioni false senza rivelare risorse non visibili.
33.6 Acceptance criteria OA-MCP
OA-MCP-01: fault producer avvenuto mentre nessun client è connesso è visibile via operations.summary dopo reconnect.
OA-MCP-02: retry multipli con stessa dedupKey producono un singolo incident aggregate con timeline bounded.
OA-MCP-03: incidente auto-risolto è restituito come RESOLVED con durata e outcome, non come failure ancora aperto.
OA-MCP-04: incidente ancora aperto espone actionRequired e stato retry senza raw secret/log.
OA-MCP-05: actor non autorizzato non può inferire existence/detail di incidenti protetti.
OA-MCP-06: partial module outage produce stato PARTIAL/UNKNOWN esplicito; il MCP non dichiara “tutto verde” in assenza di evidence.
OA-MCP-07: capability operationali rispettano timeout, pagination e hard result-size budget.
OA-MCP-08: notification live persa non causa perdita informativa perché il successivo catch-up recupera l’evento persistito.
34. Channel-neutral capability exposure and MCP owner endpoint
Normative correction v1.4. Human-facing OUF capabilities MUST NOT depend on the MCP protocol channel for availability. MCP is a governed conversational client/projection of OUF capabilities; it is not an exclusive application API, an alternative service bus, or a privileged shortcut around Urban API Gateway mediation.
34.1 Mandatory channel-neutral invariant
Any human-facing capability that can reasonably be consumed by a future UI, CLI, automation client, or MCP client MUST have a channel-neutral capability identity and a Gateway-mediated execution path.
The MCP tool registry MAY expose a conversational projection of such capability, but tool eligibility MUST NOT be the only means of invoking the underlying business/operational capability.
A capability owned by the MCP physical module remains owned by MCP, but its owner API MUST be distinct from the MCP protocol endpoint. The Gateway calls the owner API; it MUST NOT recursively re-enter /mcp.
MCP MUST NOT special-case owner=mcp by reading the datastore after admission as a substitute for Gateway dispatch. Local direct dispatch for a human-facing capability is prohibited.
Authorization, admission/budget, correlation, reconciliation, audit, redaction and tenant isolation semantics MUST remain equivalent across chatbot, UI and other approved channels.
34.2 MCP-owned Operational Awareness API
For ouf.system.status, the MCP module MUST expose a private owner endpoint, reachable only through the Gateway trust boundary, for example POST /api/internal/v1/mcp/operations/status. This endpoint is not an MCP protocol endpoint and is not Internet/publicly exposed.

OA-MCP-CN-01: ouf.system.status invoked through MCP traverses Gateway and reaches the MCP owner API, with no local-dispatch shortcut.
OA-MCP-CN-02: the same Gateway capability can be invoked by a non-MCP approved client identity when Authorization permits it.
OA-MCP-CN-03: direct access to the MCP owner API from an untrusted workload is denied by network/trust policy.

OA-MCP-CN-05: chatbot and non-chatbot paths preserve equivalent tenant isolation, redaction and NOT_AUTHORIZED/PARTIAL semantics.
