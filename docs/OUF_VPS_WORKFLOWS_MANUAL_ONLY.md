## CI e criteri di rilevamento

Trentasette workflow includono anche job GitHub-hosted. Nessuno dei 73 dichiarava `pull_request`. I job hosted di questi workflow ora seguono il dispatch insieme a quelli sul VPS, conservando le dipendenze `needs` in entrambe le direzioni. Per esempio, `declare` attende `verify`, mentre la CI Flyway attende l’artefatto acquisito sul VPS.

La guardia gira su `ubuntu-24.04` a ogni PR e push e analizza tutti i file `.yml` e `.yaml`, anche quelli aggiunti in futuro. Accetta come hosted le etichette letterali verificate nel repository. Un gruppo, un’espressione o un’etichetta sconosciuta richiedono prudenzialmente il dispatch. Le quattro chiamate locali riusabili della base puntano a workflow hosted, analizzati a loro volta. Su un workflow VPS anche `workflow_call` viola la regola. Il messaggio di errore indica file, job ed eventi. Il comando locale richiede Python 3 e PyYAML.

```shell
python3 -B tests/test_vps_workflows_manual_only.py -v
```

## Avvio manuale

1. Dopo la pubblicazione del workflow sul branch predefinito, aprire **Actions** con un account con accesso in scrittura.
2. Individuare il workflow tramite il nome della tabella. In **Run workflow**, selezionare il branch che contiene la revisione autorizzata e verificarne il commit e l’effetto atteso.
3. Con il sì di Giovanni per l’operazione sul VPS, confermare **Run workflow**. La pagina della run mostra la revisione eseguita e i singoli job. I 73 workflow censiti non dichiarano input manuali.

La guardia controlla la configurazione del candidato. Per usarne l’esito come vincolo di merge occorre che la protezione di `main` richieda il check `vps-manual-only` del workflow **VPS workflows manual only**. Le code già esistenti e i rerun di revisioni storiche seguono le rispettive definizioni.
