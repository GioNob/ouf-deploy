Decisione architetturale v1.0
L’Ingestion Runtime è un unico modulo fisico che incorpora Connector/Adapter, sincronizzazione PULL e pipeline ETL/semantic processing. Consuma esclusivamente configurazioni APPROVED/ACTIVE pubblicate dall’Onboarding, accede alle sorgenti esterne soltanto attraverso l’Urban API Gateway e non assume responsabilità di onboarding, authoring semantico, object resolution autoritativa o persistenza finale degli Urban Object.
Executive delta v1.2 — Cross-Module Alignment Freeze
La v1.2 allinea il Runtime alla Cross-Module Alignment Matrix v1.1 e alla baseline downstream Data Lake / UDP / Urban Object Registry v1.2. Il perimetro funzionale non viene ampliato: vengono congelati i contratti già necessari per l’esecuzione affidabile. Le variazioni normative riguardano Durable ACK e commit del watermark, Preflight Contract Check prima di ogni run schedulata, ChangeRepresentationProfile, isolamento dello schema drift, identità source-object per fonti INTERNAL_MANAGED/GIS e completezza dell’handoff verso la UDP. Nessun broker, graph database, lakehouse engine o nuovo prodotto infrastrutturale entra nella baseline.
Executive delta v1.3 — Persistent Operational Events & Chatbot Catch-up
La v1.3 rende normativo il percorso fault/retry/recovery → operational event persistente → capability governata → MCP/chatbot. L’Ingestion Runtime resta owner dello stato dei propri job e non espone raw log come tool MCP. Ogni failure significativa e ogni recovery devono essere ricostruibili anche quando nessun client era connesso.
1. Scopo del documento
Questo documento costituisce il Progetto Esecutivo Tecnologico v1.3 dell’Ingestion Runtime dell’Open Urban Framework. La v1.2 mantiene invariata la baseline fisica Source Connector & Adapter Framework + Sync Runtime + ETL / Ingestion e consolida la governance operativa emersa dalla review della v1.0: gestione conversazionale di issue e quarantena, sorveglianza dello schema e data-contract drift, integrazione geospaziale WFS verso il grafo urbano, file intake governato per fonti INTERNAL_MANAGED, concorrenza multiutente/multi-worker, hardening delle migrazioni Flyway e capability di lineage. Il Runtime resta configuration-driven, PULL-first per le fonti esterne, interoperabile con Gateway, Onboarding, Authorization, Semantic Registry e futuro Data Lake/UDP, senza introdurre nuovi deployable o infrastrutture dedicate incompatibili con il design constraint economico del core OUF pari a 150.000 €.
1.1 Obiettivi della baseline
Consumare PublishedConfigurationBundle e relativi runtime profile senza reinterpretare decisioni di governance.
Eseguire bootstrap, catch-up e delta PULL in modo restartable, idempotente e osservabile.
Adattare payload nativi e costruire l’OUF Canonical Data Envelope.
Applicare normalizzazione tecnica, mapping di proprietà e vocabolari, semantic enrichment e validazioni runtime configurate.
Produrre candidate canonical objects e lineage sufficienti per il successivo livello UDP / Urban Object Registry.
Gestire retry, quarantena, schema drift e failure senza perdita silenziosa dei dati.
Rimanere implementabile con Java/Spring Boot, PostgreSQL e servizi condivisi OUF, senza Kafka, Spark, Flink, NiFi o Airflow obbligatori.
Supportare fonti INTERNAL_MANAGED create da file strutturati (es. Excel/CSV) tramite staging, profiling, onboarding governato e successiva ingestione versionata.
Rendere issue, quarantena, schema drift e recovery ispezionabili e governabili tramite capability utilizzabili dall’esperienza chatbot/MCP, senza trasferire all’AI autorità di approvazione.
1.2 Non-obiettivi
Non esegue onboarding delle fonti né decide INCLUDE/EXCLUDE.
Non adotta o modifica ontologie, vocabolari, classi o relazioni nel Semantic Model / Registry.
Non materializza autoritativamente relazioni tra istanze quando è richiesta object resolution; produce input ed evidence per il livello competente.
Non è il system of record degli Urban Object canonici.
Non espone API pubbliche consumer-facing né tool MCP diretti.
Non sostituisce il Data Lake o la UDP.
Non introduce un event mesh dedicato nella baseline iniziale.

5. PublishedConfigurationBundle: contratto di esecuzione
Il Runtime non legge configurazioni parziali direttamente dalle tabelle dell’Onboarding. Consuma un bundle immutabile pubblicato, referenziato da publicationId/version/configurationHash. Il puntatore ACTIVE è risolto atomicamente e una singola ingestion run resta vincolata alla stessa versione del bundle per tutta la sua durata.
{
  "publicationId": "pub-suap-2026-001",
  "sourceId": "suap-prod",
  "configurationHash": "sha256:...",
  "extractionProfile": { ... },
  "syncProfile": { ... },
  "sourceSchemas": [ ... ],
  "propertyMappings": [ ... ],
  "vocabularyMappings": [ ... ],
  "relationshipMappings": [ ... ],
  "authorityPolicies": [ ... ],
  "semanticReferences": [ ... ]
}
5.1 Regole di consumo
Una run in corso non cambia bundle a metà elaborazione.
Una nuova versione ACTIVE viene usata soltanto da nuove run o da resume compatibili esplicitamente.
Il runtime verifica checksum/versione e fallisce fail-closed se un riferimento obbligatorio non è risolvibile.
Le secretRef rimangono riferimenti opachi; il runtime non riceve segreti dall’Onboarding.
OUF_SYSTEM/INTERNAL_MANAGED può produrre bundle senza binding PULL esterno.

7.2 Bootstrap consistente
Acquisire T0 / snapshot point / high-water mark documentato dalla Source API.
Eseguire FULL_SNAPSHOT con paging e field projection definiti dall’Extraction Profile.
Persistire checkpoint intermedi restartable senza dichiarare completato il bootstrap.
Eseguire CATCH_UP di tutte le variazioni successive a T0.
Validare errori, quarantene e coerenza minima del run.
Solo a catch-up completato, impostare il watermark operativo e abilitare DELTA.
Regola di continuità
La sequenza snapshot → catch-up → delta non può avere una finestra non osservata. Il runtime non assume una tecnologia specifica (CDC, asOf, snapshotId): applica il meccanismo dichiarato dalla Source API e configurato nel SyncProfile.
7.3 Checkpoint e commit semantics
Il checkpoint rappresenta progresso confermato, non semplice progresso letto. Per una pagina/batch, il cursor successivo può essere persistito come committedCheckpoint solo dopo che l’unità prevista dal processing contract è stata resa durevole nelle destinazioni richieste o classificata in modo esplicito come quarantena terminale ammessa dalla policy.
fetch page N
  -> adapt envelopes
  -> process records
  -> persist outputs / quarantine decisions
  -> COMMIT processing evidence
  -> advance checkpoint to page N+1
7.4 Delta e record che escono dal perimetro
Una variazione deve restare osservabile anche se porta un record da uno stato precedentemente eleggibile a uno stato non più incluso negli eligibleStates. Il runtime non può filtrare silenziosamente un evento necessario a rimuovere, chiudere o aggiornare una precedente rappresentazione canonica.

14. Idempotenza, deduplicazione e ordering
14.1 Idempotency key
La deduplicazione tecnica usa una chiave derivabile da source identity, operation/revision/change token e bundle/run context. messageId non è sufficiente se una stessa modifica viene letta due volte dopo un retry.
technicalKey = hash(
  sourceId, typeCode, sourceObjectId,
  sourceRevision | changeToken | lastModified,
  operation
)
14.2 Ordering
Non è richiesto un ordering globale tra tutte le sorgenti.
Per la stessa source identity, il runtime deve impedire che una revisione più vecchia sovrascriva una revisione già applicata quando la sorgente fornisce revision/lastModified affidabili.
Se l’ordering non è dimostrabile, l’evento viene marcato ORDER_UNCERTAIN e gestito secondo policy, non riordinato euristicamente.

Retry con exponential backoff + jitter, limiti per classe di errore e circuit breaker semplice lato connector. Il retry non avanza il committed checkpoint e deve essere idempotente.

16. Schema evolution e compatibility
16.1 Schema version change
Il payload riporta schemaId/schemaVersion sorgente.
Il Connector non accetta automaticamente una versione incompatibile non prevista dal bundle.
Una versione dichiarata backward-compatible può essere ammessa secondo schemaVersionPolicy configurata.
Una modifica strutturale breaking produce SCHEMA_INCOMPATIBLE, sospende il processing del relativo source type e apre evidence per re-onboarding.
Il runtime non modifica mapping per adattarsi al nuovo schema.
16.2 Change detection
DISCOVERED SOURCE SCHEMA VERSION != BUNDLE EXPECTED
  -> compatibility check
     -> COMPATIBLE: continue + evidence
     -> UNKNOWN/BREAKING: pause affected flow
        -> notify governance / require new onboarding version
17. OUF_SYSTEM / INTERNAL_MANAGED
OUF_SYSTEM non simula una Source API. Per acquisitionMode=MANAGED il Runtime riceve operazioni governate o batch interni tramite un adapter dedicato, costruisce lo stesso Envelope/evidence model e applica la pipeline semantica approvata. Non esegue polling né richiede route southbound inesistenti.
sourceKind = INTERNAL_MANAGED
acquisitionMode = MANAGED
sourceBinding = null
syncProfile.mode = MANAGED
connector = InternalManagedAdapter

Distinzione fondamentaleCheckpoint = posizione recuperabile all’interno di una run. Committed Watermark = frontiera che la piattaforma può usare come punto di partenza della run successiva. Un checkpoint può avanzare più volte senza rendere automaticamente committed il watermark.

32.1 Regola commit-after-durable-handoff
Il Runtime riceve il record/batch dalla sorgente tramite Gateway.
Adapter e pipeline producono output/evidence deterministici.
Il Runtime registra in transazione locale ProcessingAttempt + HandoffItem READY e il nuovo progress checkpoint candidato.
Il worker consegna l’HandoffItem al sink downstream con chiave idempotente.
Dopo ACK o equivalente durabile, l’HandoffItem passa ad ACKED e il checkpoint diventa eligible per commit.
Solo quando tutti gli item necessari nello scope sono ACKED oppure QUARANTINED secondo una policy che li considera gestiti, viene aggiornato CommittedWatermark.
No silent skipUn errore non classificato come gestito blocca l’avanzamento del committed watermark. Il sistema può continuare su altre partition indipendenti, ma non finge che lo scope fallito sia sincronizzato.

34.1 Outbox dispatch: transazioni corte e nessuna chiamata remota in TX DB
Il dispatcher dell'outbox DEVE separare il claim persistente dalla chiamata HTTP downstream. Una transazione PostgreSQL non può restare aperta mentre il worker attende la risposta della UDP o di altro downstream. Il pattern normativo è TX#1 breve per claim/stato DELIVERING, chiamata remota fuori transazione, TX#2 breve per ACKED oppure FAILED_RETRYABLE/FAILED_TERMINAL.
TX #1 — CLAIMREADY -> DELIVERINGattempts := attempts + 1delivery_owner / delivery_lease_until / delivery_started_atCOMMITHTTP / internal call verso downstreamNESSUNA transazione DB apertaTX #2 — COMPLETIONDurable ACK -> ACKED + ack_at + downstream_receipt_refretryable failure -> FAILED_RETRYABLE + next_attempt_atterminal failure -> FAILED_TERMINALCOMMIT
OUTBOX-01 — Il metodo applicativo che effettua la chiamata remota non deve essere racchiuso nello stesso @Transactional che effettua claim o aggiornamento finale dell'outbox. L'implementazione deve rendere verificabile con integration test che la connessione JDBC/lock della TX#1 sia rilasciata prima dell'I/O remoto.
OUTBOX-02 — DELIVERING è uno stato con lease, non un lock indefinito. Se il Pod termina dopo il commit della TX#1 ma prima della TX#2, alla scadenza della lease un recovery worker può reclamare l'handoff e riproporlo con lo stesso handoffId/idempotency key. Il downstream deve rendere il replay logicamente idempotente.
OUTBOX-03 — Il worker può usare SELECT ... FOR UPDATE SKIP LOCKED, UPDATE ... RETURNING o tecnica equivalente per il claim, ma deve limitare il numero di righe reclamate in base a concurrency, downstream capacity e HikariCP budget. Non è ammesso pre-claimare batch molto più grandi della capacità effettiva di dispatch.

Un contratto referenziato da una IngestionRun o da dati soggetti a retention non può essere eliminato in modo distruttivo.

45.1 Durability e ACK
Handoff state: READY → DELIVERING → ACKED oppure FAILED_RETRYABLE / FAILED_TERMINAL.
ACK significa che il downstream ha reso durevole il record o la sua reference secondo il proprio contratto; non significa necessariamente che object resolution sia completata.
Un ACK duplicato per lo stesso handoffId è idempotente.
Il committed watermark della partition non avanza oltre una sequenza contenente handoff non ACKED quando quella sequenza è richiesta dalla strategia di consistenza.
45.2 Durable ACK — semantica normativa v1.2
Il downstream emette Durable ACK quando HandoffPayload, payload/raw reference necessaria al recovery, contract references e metadati minimi di ripresa sono stati persistiti in modo durevole. L’ACK NON attende object resolution, merge, materializzazione completa dell’Urban Object o indicizzazione finale. Questo confine evita che una lunga elaborazione downstream mantenga aperta la responsabilità del Sync Runtime.
ACK-01 — Ingestion non avanza il committed watermark della partition oltre un handoff richiesto finché non riceve Durable ACK.
ACK-02 — Se il processo fallisce prima dell’ACK, la stessa finestra/record può essere riproposta; handoffId e idempotency key rendono il replay logicamente idempotente.
ACK-03 — Un ACK ricevuto dopo retry o duplicato non crea un secondo commit logico.
ACK-04 — Il downstream può completare resolution/materialization dopo l’ACK; un errore successivo è responsabilità UDP e viene correlato tramite handoffId/lineageId.
ACK-05 — Non è ammesso interpretare HTTP 202 del Gateway, scrittura in memoria, enqueue locale o sola validazione schema come Durable ACK.

Se il campo non è presente in bundle storici, il default compatibile è FULL_SNAPSHOT.

50. Downstream consistency e responsabilità UDP

La v0.4 consolida il comportamento operativo dell’Ingestion Runtime sotto carico senza ampliare il perimetro funzionale. Il focus è rendere prevedibili throughput, latenza, consumo di risorse, backlog, retry, fairness tra fonti e degradazione controllata. Le decisioni qui congelate sono coerenti con il design constraint economico OUF: nessun broker, motore di stream processing o scheduler esterno è richiesto per soddisfare la baseline iniziale.
Definire un performance envelope iniziale misurabile e verificabile in staging.
Impedire che una sorgente lenta, rumorosa o in errore degradi tutte le altre sorgenti.
Applicare backpressure prima di saturare database, memoria, pool HTTP o downstream.
Separare SLO interattivi delle API operative dagli SLO dei job asincroni.
Definire overload behavior, circuit breaking, retry budget e recovery time.
Confermare che PostgreSQL-backed scheduling/handoff resti sufficiente per il core iniziale.
Decisione v0.4 — il Runtime privilegia stabilità e correttezza rispetto al throughput massimo. In overload rallenta o sospende l’acquisizione, preserva checkpoint e lineage e non perde silenziosamente record. Il delta watermark avanza solo dopo durable handoff.

54.1 Principio di sizing
Il throughput non viene ottenuto aumentando indefinitamente la concorrenza.
Il primo controllo di scala è il parallelismo tra fonti; il secondo è la partizione per dataset/source type.
La concorrenza intra-source è ammessa solo quando il protocollo sorgente e la semantica di ordering lo consentono.
Qualunque aumento di replica deve preservare lease, deduplication e checkpoint semantics definite in v0.2.
Il profilo iniziale deve poter funzionare su nodi Kubernetes standard condivisi, senza worker pool dedicati ad alte prestazioni.

55.1 Watermark di pressione
NORMAL -> SOFT_PRESSURE -> HARD_PRESSURE -> RECOVERY
SOFT_PRESSURE: riduzione concurrency/pageSize, nessuna perdita
HARD_PRESSURE: stop admission nuove run, pull sospeso per fonti non prioritarie
RECOVERY: riapertura graduale; niente thundering herd
Le soglie sono configurazione operativa e possono differire per ambiente.
Il passaggio HARD_PRESSURE non modifica PublishedConfigurationBundle o mapping.
Il sistema non avanza progress/watermark su record non durable.
Il recovery è graduale e soggetto a hysteresis per evitare oscillazioni continue.

68. Payload safety e parser hardening
I payload sorgente sono input non fidati. La v0.5 congela controlli minimi indipendenti dal protocollo specifico.
Limite configurabile su response body, singolo record, numero record per pagina e profondità JSON/XML.
Parsing streaming per payload potenzialmente grandi; evitare materializzazione integrale in memoria quando non necessaria.
XML: DTD e external entity disabilitate; nessun fetch di schema remoto durante il processing.
Compressione: limiti su compressed/uncompressed ratio e dimensione finale; archive traversal non ammesso.
JSON: limiti su nesting e token; numeri/data fuori range producono validation issue, non overflow silenzioso.
Geo: CRS, coordinate range e geometry complexity sottoposti a limiti; geometrie invalide seguono quarantine/validation policy.
Content-Type inatteso o schemaVersion non compatibile non viene reinterpretato euristicamente.
Log e metriche non contengono payload completi, token, secret o URL con credenziali.

83.1 Flyway production execution policy
In produzione spring.flyway.enabled sui normali Pod applicativi DEVE essere disabilitato per l'operazione migrate. Le migration sono eseguite una sola volta da un Kubernetes Job, pipeline step o meccanismo equivalente governato dalla release. I Pod applicativi eseguono soltanto schema compatibility/readiness checks e possono eseguire validate se previsto dal profilo operativo, ma non modificano lo schema come side effect dello startup.
DBMIG-01 — Il rollout N+1 non può iniziare finché il migration job della fase prevista non è terminato con successo e la versione dello schema è dichiarata compatibile con la mixed-version window. Un fallimento migration blocca il rollout; non viene risolto avviando comunque i Pod e lasciando loro tentare migrate.

94. Retry exhaustion, circuit breaker e retry budget
Il retry è consentito esclusivamente per failure classificate retryable. Ogni source/binding dispone di un retry budget finito per finestra temporale; il superamento del budget apre il circuit breaker e impedisce loop infiniti.
Backoff esponenziale con jitter; rispetto di Retry-After quando presente e valido.
Tentativi e nextRetryAt sono persistiti; un restart del pod non azzera il budget.
Il retry di handoff downstream è separato dal retry di fetch sorgente.
Dopo exhaustion: stato DEGRADED o PAUSED secondo policy; nessun record viene scartato automaticamente.
retryState = { attempts, firstFailureAt, lastFailureAt, nextRetryAt, budgetWindow, circuitState }

98. Replay safety e recovery amministrativo
Le operazioni di replay non modificano retroattivamente i record storici. Ogni replay è una nuova execution evidence che dichiara modalità, contratti usati e motivo. Le modalità REPRODUCE, REPROCESS_CURRENT e REPROCESS_TARGET definite nella v0.3 restano normative.
REPRODUCE usa bundle/schema/mapping/adapter storici per riprodurre il comportamento originario.
REPROCESS_CURRENT usa il raw storico ma la configurazione ACTIVE corrente; non sostituisce la lineage originaria.
REPROCESS_TARGET usa una baseline esplicitamente indicata e risolvibile.
Ogni replay è idempotente rispetto alla propria idempotency key, ma non viene confuso con la run originaria.
La cancellazione di contratti storici referenziati da raw/lineage/replay è vietata.
99. Source, downstream e infrastructure outage
99.1 Sorgente indisponibile
Una indisponibilità temporanea della sorgente non rende il pod unhealthy. La source health può risultare DEGRADED mentre il servizio resta ready per altre fonti. Solo fault locali essenziali (es. DB operativo non disponibile oltre policy) incidono sulla readiness del workload.
99.2 Downstream indisponibile
Se Data Lake/UDP non accettano handoff, il runtime smette progressivamente di acquisire nuovi dati tramite backpressure. I record già trasformati restano nell’outbox persistente; il committed watermark non supera il confine dell’handoff durevole.
99.3 Database operativo indisponibile
Il runtime non prosegue in modalità best-effort senza persistenza. Nuovi fetch vengono sospesi; al ripristino, lease/checkpoint/outbox determinano il resume sicuro.
100. Graceful shutdown, lease recovery e deployment safety
Su SIGTERM il worker interrompe l’acquisizione di nuovi batch, completa la transazione corrente entro terminationGracePeriodSeconds e rilascia/lascia scadere la lease in modo sicuro.
Nessun shutdown aggiorna il committed watermark se il relativo handoff non è durable.
Pod replacement e rolling update devono essere testati con run in corso, outbox pending e quarantine aperta.
La lease ha scadenza; un worker morto non mantiene lock indefiniti.
La nuova versione applicativa deve poter leggere lo stato persistito dalla versione precedente secondo la compatibility policy.
101. RuntimeIssue e audit evidence v1
Ogni failure rilevante genera o aggiorna un RuntimeIssue con scope, severità, codice stabile, resourceRef, firstSeen/lastSeen, contract refs e remediation state. Log testuali non costituiscono l’unica evidenza del problema.

103. Failure semantics — decisioni normative
La rete interna o il cluster non trasformano una failure di autenticazione in una chiamata trusted.
Il committed watermark avanza soltanto dopo durable handoff del perimetro previsto dalla strategy.
Il retry automatico è limitato alle categorie esplicitamente retryable e a un budget finito.
Quarantine non significa perdita: conserva raw reference, lineage, contratti e failure evidence.
PAUSE è reversibile; ABORT è terminale; RESUME non cambia il bundle pinning della run.
Una run può essere COMPLETED_WITH_WARNINGS soltanto quando le eccezioni residue sono esplicite, non-blocking e auditabili.
Replay e reprocessing producono nuova provenance e non riscrivono la storia.
Contratti storici necessari a retention, audit o replay restano risolvibili e non sono eliminabili distruttivamente.
Fault di una singola sorgente non devono rendere indisponibile l’intero Ingestion Runtime per le altre sorgenti.
Nessuna nuova infrastruttura di messaging è richiesta per implementare queste semantiche nella baseline.
La v0.8 congela il modello di compatibilità dell’Ingestion Runtime. Tutti i contratti eseguibili e di handoff vengono trattati come artefatti versionati, testabili e storicamente risolvibili. L’obiettivo non è aggiungere funzionalità, ma impedire che evoluzioni indipendenti di Source API, Onboarding, Semantic Registry, Adapter, processing pipeline o UDP rompano run attive, replay storici o consumer già distribuiti.
Decisione normativa v0.8Compatibilità e versionamento sono parte del contratto operativo, non una convenzione informale. Nessuna modifica può essere dichiarata “compatibile” senza contract test e consumer compatibility test.

106. PublishedConfigurationBundle compatibility
Una IngestionRun pinna una singola versione immutabile del PublishedConfigurationBundle. Il bundle ACTIVE può avanzare soltanto per run future. Il Runtime non effettua hot-reload di mapping, schema reference o processing profile dentro una run già iniziata.
Il consumer deve poter recuperare esplicitamente una versione storica del bundle tramite identificativo/versione.

114. Deprecation, support window e removal policy
La deprecazione è esplicita e non equivale a cancellazione. Un contratto o Adapter deprecato resta risolvibile per il periodo necessario a run attive, historical replay e retention dei dati che lo referenziano.
DEPRECATED: non usato per nuove configurazioni salvo eccezione governata; continua a funzionare per storico.
SUPPORTED: ammesso per nuove run e replay.
RETIRED: non ammesso per nuove run, ma può restare materializzato/archiviato per prova e riproducibilità.
REMOVED: possibile solo dopo dependency scan che dimostri assenza di riferimenti soggetti a retention/replay o dopo migrazione esplicita.
La removal policy non può essere basata soltanto sull’età del componente.

132. Runtime invariants — freeze definitivo
I seguenti invarianti costituiscono il nucleo non negoziabile della v1.0.
Una IngestionRun usa una sola PublishedConfigurationBundle version per l’intero ciclo, inclusi pause/resume e recovery.
Progress checkpoint e committed watermark sono concetti distinti; il secondo avanza soltanto dopo durable handoff downstream.
Snapshot, catch-up e delta devono essere concatenabili senza perdita delle variazioni previste dal contratto della Source API.
Ogni record acquisito resta riconducibile a source identity, source schema version, configuration bundle, mapping/profile version e semantic publication set usati.
Schema drift non produce mai auto-remapping: apre issue e, se necessario, nuovo onboarding.
Retry e replay non devono produrre duplicazioni logiche downstream; handoffId e idempotency evidence sono obbligatori.
Quarantine non equivale a cancellazione: conserva evidence sufficiente a diagnosi, replay e audit.
Una service identity non è un HUMAN_USER e la posizione nella rete/cluster non sostituisce autenticazione/autorizzazione.
Il Runtime consuma semantica pubblicata ma non esegue authoring, discovery o adozione semantica.
Object Resolution finale e materializzazione delle relazioni ABox restano nel boundary UDP / Urban Object Registry.

139.1 Cross-Module Alignment Acceptance Addendum v1.2
ING-A01 — Durable ACK: watermark non avanza prima della persistenza durevole downstream di payload/reference + recovery metadata; object resolution può completare dopo ACK.
ING-A02 — Crash before ACK: la stessa finestra viene replayata senza duplicazione logica downstream.
ING-A03 — Preflight unchanged: schema fingerprint/ETag invariato evita full schema discovery e la run procede.
ING-A04 — Preflight breaking drift: solo type/partition impattato viene sospeso/quarantinato; watermark non oltrepassa l’incompatibilità.
ING-A05 — Historical continuity: dopo attivazione bundle vNext, record precedenti restano riproducibili con contract chain originale.
ING-A06 — FULL_SNAPSHOT compatibility: bundle storico privo di ChangeRepresentationProfile viene interpretato come FULL_SNAPSHOT.
ING-A07 — DELTA_PATCH handoff: base reference/hash viene preservato e il Runtime non legge lo stato canonico UDP per ricostruire il delta.
ING-A08 — INTERNAL_MANAGED file: dataset identity e sourceObjectId delle righe restano distinti; ogni riga può produrre 0..N candidate.
ING-A09 — GIS file: GeoPackage/GeoJSON/Shapefile/CSV-WKT validi attraversano intake→onboarding→runtime con CRS/feature provenance preservati.
ING-A10 — WMS boundary: un layer WMS non viene trattato automaticamente come dataset di feature ingestibile.
ING-A11 — Cross-module contract: HandoffPayload contiene bundle/schema/mapping refs, source-object identity, lineage e access labels richiesti dalla UDP v1.2.
ING-A12 — Scope isolation: drift o errore su un procedure/type non arresta source/type indipendenti quando il bundle consente isolamento.
ING-A13 — Outbox no remote-in-TX: il dispatcher committa READY→DELIVERING e rilascia la connessione/lock DB prima di invocare il downstream; ACKED/FAILED viene scritto in una seconda transazione corta.
ING-A14 — DELIVERING crash recovery: crash del Pod tra TX#1 e TX#2 lascia un item reclamabile dopo lease expiry; il replay usa lo stesso handoffId e non produce doppio effetto logico downstream.
ING-A15 — Flyway production gate: con 2+ Pod applicativi in rolling update nessun Pod esegue migrate; un unico migration job governa lo schema e il rollout resta bloccato su migration failure.
ING-A16 — Expand/Contract mixed-version: durante il rollout lo schema intermedio è compatibile simultaneamente con N e N+1; un CONTRACT distruttivo non è eseguibile finché workload N possono essere attivi.
ING-A17 — Migration readiness: appVersion/schemaVersion/compatibilityRange incoerenti rendono il Pod NOT_READY prima di servire workload.
140. Technology Economy Gate
Il design constraint di 150.000 € riguarda l’intero core OUF e resta un requisito architetturale. L’Ingestion Runtime è quindi congelato nella forma più semplice che soddisfa i contratti e i requisiti non funzionali iniziali.
Connector + Adapter + Sync + ETL restano un solo modulo fisico iniziale.
PostgreSQL svolge stato operativo, checkpoint, outbox e quarantine metadata senza introdurre un broker dedicato.
Kubernetes, IAM, secret manager, observability e CI/CD sono servizi trasversali riusati.
Data Lake / object storage è downstream condiviso e non viene duplicato nel Runtime.
Una proposta di Kafka/NATS/RabbitMQ, Redis, Spark/Flink, Airflow/NiFi, service mesh o prodotto lineage dedicato deve essere accompagnata da failure evidence o requisito misurabile non soddisfatto dalla baseline.
La futura scalabilità può separare fisicamente bounded context senza cambiare i contratti v1 quando il carico lo giustifica.

142.3 Preflight Contract Check — obbligatorio per ogni run schedulata
Prima di acquisire dati, ogni scheduled run esegue un controllo contrattuale leggero contro la sorgente e il bundle pinning. Lo scopo è intercettare drift prima di elaborare una finestra dati con un contratto non più valido. Il preflight non equivale a riscoprire integralmente lo schema a ogni run.
PRE-FLIGHT
1. source/capability disponibile e ammessa
2. typeCode/sourceType ancora esistente e ACTIVE
3. schemaVersion / schemaFingerprint / catalogVersion / ETag lightweight check
4. confronto con PublishedConfigurationBundle pinning
5. unchanged/compatible -> acquisizione
6. changed -> full discovery solo per scope cambiato
7. breaking -> pause/quarantine dello scope impattato + RuntimeIssue + Onboarding review
PREF-01 — Se la Source API espone ETag/version/fingerprint affidabile, il Runtime NON scarica lo schema completo quando tali indicatori sono invariati.
PREF-02 — Un drift breaking non blocca automaticamente source/type non impattati: l’unità di isolamento è la più piccola partition/type/procedure compatibile con il contratto.
PREF-03 — Nessun watermark viene avanzato oltre record acquisiti con contratto dichiarato incompatibile.
PREF-04 — La nuova OnboardingVersion può riutilizzare mapping compatibili come proposta, ma l’attivazione del nuovo PublishedConfigurationBundle resta human-governed.
PREF-05 — I record storici restano riproducibili con Historical Contract Model e bundle/schema originari.

146. Database Migration Safety Policy — Flyway e rollout concorrenti
Flyway è lo strumento di versionamento dello schema, non la strategia completa di sicurezza del rollout. In produzione le migration devono essere eseguite da un unico migration job/pipeline governato; i pod applicativi validano la versione dello schema e non competono indiscriminatamente per modificare il database durante lo startup.

Application startup

Failure

Checksum drift
Deployment BLOCKED finché la divergenza non è investigata e governata.

146.1 Expand / Contract come protocollo normativo di rolling update
Ogni modifica DDL che può interferire con una finestra Kubernetes in cui convivono release N e N+1 DEVE seguire un pattern Expand/Contract. Lo schema intermedio deve essere consumabile da entrambe le versioni applicative. Rename distruttivi, DROP di colonne/constraint o cambi di tipo incompatibili non vengono eseguiti nello stesso rollout che introduce il nuovo codice.
FASE EXPAND1. aggiunta strutture nuove compatibili2. eventuale backfill restartable / checkpointed3. schema READY per N e N+1ROLLOUT N+14. deploy progressivo5. dual-read/dual-write o compatibility adapter dove necessario6. smoke + conformance + osservazione mixed-versionFASE CONTRACT — release successiva7. verifica che nessuna istanza N possa più essere attiva8. rimozione strutture legacy9. validate + backup/PITR evidence
DBMIG-02 — Una migration di tipo CONTRACT è ammessa solo quando la piattaforma può dimostrare che non esistono workload compatibili esclusivamente con lo schema precedente. Il readiness gate deve fallire in modo esplicito se appVersion, schemaVersion o compatibility range non sono coerenti.
DBMIG-03 — Data migration pesanti devono essere separate dal DDL quando possibile, eseguite come job restartable e osservabili. Operazioni PostgreSQL con semantica non transazionale o lock potenzialmente lunghi richiedono migration dedicata, timeout/lock policy e runbook di recovery.

46. Persistent Operational Event Model
46.1 Producer obligations
Ogni run schedulato o manuale mantiene JobStatus persistente e correlationId stabile.
Transizioni significative QUEUED/RUNNING/RETRY_WAIT/FAILED/CANCELLED/SUCCEEDED devono produrre o aggiornare un operational incident aggregate quando esiste impatto utente/operativo.
Un retry transient non produce automaticamente un nuovo incidente; si aggiorna lo stesso incidentId/dedupKey finché la causa operativa rimane equivalente.
Una recovery dopo RETRY_WAIT chiude l’incidente come RESOLVED indicando firstSeenAt, resolvedAt, attempt count e outcome safe-for-user.
Failure terminale mantiene lifecycleState OPEN fino a remediation/re-run governato o esplicita risoluzione.
Eventi e incidenti devono essere persistiti nel datastore Ingestion già adottato; non è richiesto un broker/event store dedicato.

46.3 Query projection for MCP
L’Ingestion Runtime DEVE offrire una API interna governata per status/history/incident projection; tale API non è pubblica consumer-facing.
La proiezione deve supportare filtri sourceRef, jobId, lifecycleState, severity, since/until e pagination bounded.
Il risultato deve esporre errorCode stabile e impactSummary redatta; raw exception/stack trace resta telemetria interna salvo policy privilegiata.
Il Gateway media la chiamata MCP→Ingestion; nessun direct bypass.
46.4 Retention and evidence
Gli incidenti RESOLVED devono essere conservati almeno quanto necessario a coprire la finestra operativa di catch-up definita dalla configurazione runtime; hard minimum baseline: 30 giorni, salvo retention più lunga già richiesta da audit/lineage.
Eventi referenziati da audit, lineage, legal hold o incident investigation non possono essere eliminati finché la referenza resta valida.
La retention deve essere bounded e non può compromettere i record di lineage autoritativi.
46.5 Acceptance OA-ING
OA-ING-01: scheduled source unavailable → RETRY_WAIT + persistent incident + nextRetryAt.
OA-ING-02: retry success → same incidentId RESOLVED, no duplicate incident storm.
OA-ING-03: terminal failure remains queryable after client reconnect.
OA-ING-04: scheduler misfire is distinguishable from source failure.
OA-ING-05: unauthorized source status is not disclosed through MCP projection.
OA-ING-06: incident retention survives process/pod restart and is independent from live notification delivery.
