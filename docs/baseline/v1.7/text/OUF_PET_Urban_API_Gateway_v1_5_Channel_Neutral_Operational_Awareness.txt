Progetto esecutivo tecnologico del modulo Urban API Gateway. La versione 1.4 mantiene la baseline architetturale e tecnologica v1.2, ma consolida il documento in forma development-ready secondo il gold standard Ingestion Runtime: configuration contract, publication atomicity, compatibility, identity binding, readiness/reference gates, DR, Secure SDLC, runbook ed evidence package.
Stato del documentoDEVELOPMENT READY v1.3 - baseline architetturale/tecnologica consolidata; contratti, deployment, operations, compatibility, IAM/M2M integration gate e acceptance allineati al gold standard Ingestion.
Executive delta v1.3 — Implementation Readiness Consolidation
La v1.3 assume l’Ingestion Runtime v1.2 come gold standard di completezza esecutiva. Non modifica la scelta APISIX/etcd/Kubernetes, il modello northbound/southbound, la separazione tra Gateway e trasformazione dati, né l’ownership di Source Onboarding, Authorization, Ingestion, Semantic Registry e UDP. La revisione consolida la baseline normativa corrente, chiude la stratificazione storica, formalizza il percorso Git/GitOps -> config compilation -> APISIX/etcd activation, introduce compatibility manifest e support window, runtime configuration catalog, identity/M2M binding, readiness/reference integrity gate, DR/evidence package, graceful drain e Secure SDLC per eventuali custom image/plugin.
Executive delta v1.2 — Cross-Module Alignment
La v1.2 allinea l'Urban API Gateway alla Cross-Module Alignment Matrix v1.1 e alle Executive Freeze di UDP v1.2, Ingestion Runtime v1.2, Source Onboarding & Configuration v1.3 e Authorization & Access Control v1.3. Il perimetro non viene ampliato: il Gateway resta boundary enforcement point per traffico esterno, autenticazione, autorizzazione coarse-grained, route binding, rate limiting, payload controls, streaming, correlation e protocol governance. Non acquisisce responsabilità di fine-grained data authorization, Query Complexity Governor, Durable ACK, schema drift classification, ETL, Object Resolution, semantic mapping o materializzazione UDP.
Executive delta v1.5 — Operational Event Boundary
La v1.5 rende il Gateway producer e transport boundary della Operational Awareness. Il Gateway emette eventi persistibili per degradazioni di propria ownership (publication blocked, etcd degradation, upstream unreachability, trust/JWKS/credential failures) e media le query MCP verso i producer. Non espone raw APISIX/etcd telemetry al chatbot e non diventa il repository centrale degli incidenti.
1. Scopo e contesto
L’Urban API Gateway costituisce il punto obbligatorio di attraversamento del confine OUF per tutte le comunicazioni tra sistemi esterni e servizi interni. Nel core iniziale devono transitare dal Gateway i dati provenienti da SUAP, SUO e SUE, i servizi geospaziali provenienti dai WebGIS (inizialmente WFS e WMS) e le future richieste dei consumer verso le capability pubblicate dall’OUF.
Il Blue Paper attribuisce al Governed Service Exposure / Urban API Gateway routing, versioning, TLS, autenticazione, rate limiting, logging, correlation ID, gestione standard degli errori ed esposizione controllata di API, OGC, bulk ed eventi. Il Gateway non implementa ETL o logica di business e non espone accesso diretto allo storage.
Vincolo architetturaleNessun sistema esterno comunica direttamente con Adapter, ETL, Semantic Model, UDP o Data Lake. Ogni attraversamento del confine OUF passa dal Gateway o da un binding equivalente governato previsto dal medesimo perimetro.

3. Principi architetturali
Gateway come boundary enforcement point: controlla ogni attraversamento del confine OUF.
Separazione tra contratto/esposizione e logica di trasformazione: il Gateway valida e instrada, gli Adapter e l’ETL trasformano.
Northbound e southbound sono due profili logici dello stesso confine governato. Il modello operativo è ibrido: l’acquisizione dalle sorgenti autorevoli è prevalentemente PULL, mentre la fruizione verso consumer può essere sincrona, streaming o PUSH/event-driven quando richiesto.
Configurazione e policy sono versionate e gestite come codice.
Nel profilo iniziale il patrimonio ammesso è OPEN o ANONYMOUS; l’architettura resta estendibile a classificazioni più restrittive.
I protocolli legacy sono ammessi ai bordi; il modello canonico interno privilegia JSON.

4.2 OUF Canonical Data Envelope
Regola di confine: il formato OUF Canonical Data Envelope è un contratto interno Adapter → ETL / Ingestion. Non è un requisito imposto ai sistemi verticali e non è il contratto northbound del Gateway.
Ogni record o batch acquisito da SUAP, SUO o SUE viene trasformato, all’interno della piattaforma OUF e dopo il superamento dei controlli di bordo del Gateway, in un OUF Canonical Data Envelope standard. I sistemi sorgente non sono tenuti a produrre direttamente tale envelope: continuano a esporre o inviare il dato nel formato nativo concordato (JSON, XML, API proprietaria, file o altro binding ammesso). La responsabilità di costruire l’envelope, separando metadati tecnici e di governance dal payload sorgente, appartiene all’Adapter / Connector Framework.

4.3 Identità dell’oggetto sorgente
Per sorgenti multi-procedimento l’Adapter costruisce nell’envelope l’identità tecnica dell’oggetto o procedimento sorgente, senza confonderla con la classificazione canonica OUF. I campi sourceObject sono derivati dal payload nativo e/o dal Source Manifest, appartengono al dominio sorgente e costituiscono input per il successivo mapping semantico.
"sourceObject": {  "type": "SUAP_PROC_047",  "instanceId": "SUAP-2026-00018453",  "procedureCode": "047"}
Il Gateway valida soltanto gli elementi disponibili al confine e dichiarati nel contratto di bordo (identità tecnica del chiamante, route, media type, dimensione, header e parametri ammessi). La valorizzazione e la validazione di sourceObject avvengono nell’Adapter dopo il parsing del formato sorgente. Né il Gateway né l’Adapter traducono autonomamente sourceObject.type in una classe canonica: la classificazione OUF viene risolta dal processing semantico tramite mapping approvati, ontologie e vocabolari controllati.
5. Identificatori, idempotenza e correlazione
Ogni chiamata di ingestion deve essere associata a un correlation ID, generato o propagato dal Gateway. La chiave di idempotenza può essere fornita dalla sorgente quando disponibile oppure derivata dal Connector secondo il Source Manifest. Il messageId dell’OUF Canonical Data Envelope viene assegnato dall’Adapter / Connector Framework. MessageId e Idempotency-Key concorrono a impedire l’elaborazione duplicata dello stesso messaggio; la deduplicazione tecnica resta distinta dalla object resolution, che valuta se record differenti descrivono lo stesso oggetto urbano.

7. Modello operativo ibrido: PULL per acquisizione, PUSH per fruizione
7.1 Acquisizione prevalente PULL dalle sorgenti
Nel core iniziale SUAP, SUO, SUE e le sorgenti WebGIS sono considerate sorgenti autorevoli passive: non devono conoscere l’esistenza dell’OUF e non devono implementare callback o webhook dedicati. Un servizio interno di Source Synchronization / Scheduler, governato dalla Source Configuration, avvia periodicamente le richieste di acquisizione. Il Connector invoca il profilo southbound del Gateway, che applica egress allowlist, autenticazione tecnica, TLS, timeout, retry e audit prima di raggiungere il verticale.
SUAP / SUO / SUE        ↓ Urban API Gateway        ↓    Ingestion API        ↓ Adapter / Connector
7.2 Ingress PUSH: supportato ma non prevalente
Gli endpoint northbound di ingestion restano disponibili per integrazioni future o sorgenti che richiedano PUSH, ma non costituiscono il meccanismo ordinario per SUAP, SUO e SUE. In tale caso il sistema esterno invia il payload nativo al Gateway, che applica i controlli di bordo e lo inoltra all’Adapter/Connector Framework; l’OUF Canonical Data Envelope viene creato dall’Adapter, non dalla sorgente.
Connector OUF     ↓Gateway southbound / External Service Proxy     ↓Sistema esterno / WebGIS

11.4 Extraction Profile e confine di responsabilità
L’Extraction Profile è prodotto e approvato dal modulo Source Onboarding / Source Configuration. Esprime, in forma eseguibile, ciò che la piattaforma è autorizzata a richiedere alla sorgente. Il Gateway non decide il contenuto del profilo e non determina la classificazione dei campi; applica il profilo alla richiesta southbound, componendo esclusivamente filtri, parametri, paging e field projection ammessi. La Source API del verticale esegue materialmente la projection e restituisce soltanto i campi richiesti.
Il profilo runtime può includere: sourceId, endpoint/protocollo, sourceType scope, stati sorgente da interrogare, query template, field projection/allowlist, paging, change token o watermark, timeout, rate limit e riferimenti a credenziali.
La classificazione dei campi (OPEN, ANONYMOUS, PERSONAL, SENSITIVE o altre categorie), l’associazione a ontologie/vocabolari e le regole di trasformazione restano nel modulo di onboarding e nei moduli semantici. Il Gateway riceve solo l’esito compilato: quali campi e parametri sono ammessi nella richiesta alla sorgente.
Per il core iniziale, l’Extraction Profile deve impedire che il Gateway richieda campi esclusi dall’onboarding. La field projection è quindi un vincolo tecnico di minimizzazione applicato sulla richiesta: il Gateway non deve ricevere il payload completo per filtrarlo successivamente. La classificazione che ha prodotto l’allowlist resta esclusivamente nella piattaforma Smart City / OUF.
Adapter, ETL e Semantic Model consumano gli ulteriori riferimenti prodotti dall’onboarding (schema sorgente, processing profile, semantic mapping) secondo i rispettivi contratti. Tali riferimenti non devono essere interpretati né modificati dal Gateway.
sourceId: suap-prodextractionProfileId: suap.concluded-procedures.v1version: 1.0.0runtime:  mode: PULL  endpointRef: suap-procedures-api  sourceTypeScope: ["*"]  sourceStatusFilter: ["<codici-stato-compilati-da-onboarding>"]  fieldProjectionRef: suap.allowed-fields.v1  incrementalStrategy: CHANGE_TOKEN  pageSize: 500processingRefs:  adapterProfileId: suap-adapter-v1  semanticMappingSetId: suap-semantic-mappings-v1
I riferimenti processingRefs sono opachi per il Gateway. Il Source Onboarding / Source Configuration può evolvere in futuro con frontend dedicato, workflow umano o assistenza AI/MCP senza modificare il perimetro del Gateway: cambia l’artefatto approvato pubblicato al runtime, non la responsabilità del Gateway.
11.5 Allineamento allo standard OUF Source API v2.1
Lo standard OUF Source API mantiene il verticale semanticamente neutro: semantica, classificazioni, ontologie, vocabolari controllati e mapping restano nella piattaforma Smart City / OUF. Il Gateway conosce solo la configurazione tecnica compilata necessaria a effettuare il PULL.
Continuità bootstrap/delta: quando il Source Sync usa snapshot iniziale e catch-up incrementale, il Gateway deve propagare senza alterazioni gli eventuali parametri tecnici di coerenza previsti dalla Source API (ad es. asOf, high-water mark, snapshot token o change token). La garanzia che nessuna modifica venga persa tra snapshot e delta appartiene al contratto Source API / Source Sync; il Gateway garantisce trasporto, routing, retry controllato e audit.
Uscita dal perimetro: il Gateway non deve sopprimere o filtrare a posteriori una variazione restituita dalla Source API solo perché il nuovo stato non appartiene più agli eligibleStates. Se un record già estraibile viene riaperto, annullato o comunque esce dal perimetro, la variazione deve essere inoltrata all’Adapter / Connector Framework per il trattamento applicativo.
Rilettura e idempotenza: retry o resume possono comportare la rilettura della stessa finestra incrementale. Il Gateway non assume garanzie exactly-once; preserva cursor, watermark/change token e correlation ID, mentre deduplicazione e idempotenza di elaborazione appartengono ai componenti di sincronizzazione e processing.

13.1 Autenticazione proposta
Per SUAP, SUO e SUE il meccanismo preferito è OAuth 2.0 Client Credentials. Quando non supportato dal verticale è ammesso mTLS; per integrazioni a maggiore criticità è possibile combinare mTLS e OAuth2 client credentials.

20. Capability Model e predisposizione MCP
Il Gateway viene progettato fin dalla prima release come punto di enforcement di capability governate, non come semplice catalogo di endpoint. Ogni servizio consumer-facing deve essere associato a una capability registrata, stabile e versionata. La capability descrive cosa offre l’OUF; REST, OGC e, in futuro, MCP costituiscono binding tecnici della stessa capacità.
Principio vincolante
Il Gateway non pubblica endpoint isolati: ogni endpoint consumer-facing deve essere associato a una capability registrata e versionata. MCP potrà esporre come tool esclusivamente capability esplicitamente abilitate, senza introdurre accessi diretti a UDP, Data Lake o sistemi verticali.

Le route geospaziali non rappresentano la capability in sé. 23. Predisposizione MCP
Il core iniziale non richiede l’attivazione di MCP. Deve però essere predisposto affinché l’introduzione futura di un MCP Server non richieda nuove API o accessi diretti ai dati. L’MCP Server fungerà da binding agentico di capability già registrate e governate.
Agent Host   ↓MCP Server   ↓ capabilityIdUrban API Gateway   ↓Backend / UDP Data Service
23.1 Regole MCP
Default deny: una capability non è esposta via MCP finché mcp.toolEligible non è esplicitamente true.
Il tool MCP deve riferirsi a un capabilityId stabile, non direttamente a URL, tabelle o feature type fisici.
Gli scope IAM della capability restano validi anche per il consumo MCP.
Le capability di tipo command o propose richiederanno in futuro policy più forti e, quando previsto, Workflow/Human Validation.
MCP non accede direttamente a UDP, Data Lake, database, WFS origin o sistemi verticali.
Audit e correlation ID devono attraversare Agent Host, MCP Server, Gateway e backend.
23.2 Capability di ingestion
Anche le funzioni tecniche di ingestion possono essere registrate come capability interne (es. source.suap.activities.ingest), ma per default non sono eleggibili come tool MCP. Questo permette un modello di governance uniforme senza esporre operazioni tecniche agli agenti.

Il Gateway deve essere predisposto fin dalla prima release al collegamento con Source Onboarding / Source Configuration, Adapter / Connector Framework, ETL / Ingestion e Urban Data Platform. Il Gateway consuma artefatti runtime approvati; onboarding, classificazione dei campi, semantica e approvazione umana restano esterni al suo perimetro.
Principio vincolanteIl Gateway instrada verso capability interne approvate. La risoluzione del binding tecnico verso Connector Framework, ETL o servizi UDP è configurata e versionata; il Gateway non diventa un orchestratore di pipeline e non conosce database, code, tabelle o dettagli implementativi interni.

27.4 Tipi sconosciuti, mapping mancanti e quarantena
La pipeline distingue tra errore tecnico di discriminazione e assenza di mapping semantico. Il Gateway espone l'esito tramite la status API ma non tenta classificazioni euristiche.
UNKNOWN_SOURCE_TYPE: il tipo sorgente non è riconosciuto dal profilo tecnico prodotto dall’onboarding. Il record non viene promosso e viene segnalato al modulo Source Onboarding / Source Configuration per revisione.
UNMAPPED_SEMANTIC_CONCEPT: il tipo sorgente è riconosciuto, ma manca un mapping semantico approvato prodotto dall’onboarding/semantic governance. Il record è posto in quarantena semantica; il Gateway non interviene nella risoluzione.
SEMANTIC_MAPPING_INVALID: mapping presente ma non valido o incompatibile con lo schema/versione semantica attiva. La gestione appartiene a ETL/Semantic Model/Onboarding, non al Gateway.
Solo gli stati semanticamente validati possono proseguire verso la promozione UDP; l'eventuale raw landing resta responsabilità della pipeline/UDP e non del Gateway.
28. Integrazione con Urban Data Platform
La UDP costituisce il patrimonio integrato e governato e mette a disposizione persistenza, ricerca, storico, catalogo, lineage e servizi dati. Il Gateway non accede allo storage fisico della UDP: instrada soltanto verso data service e capability approvate.
28.1 Scrittura verso UDP
La scrittura nella UDP è responsabilità della pipeline ETL/ingestion o di un servizio backend dedicato. Il Gateway non effettua persistenza diretta.

31. Criteri di collaudo
Il Source Sync può eseguire un bootstrap PULL completo da SUAP, SUO e SUE attraverso il Gateway southbound.
Ogni ciclo PULL usa esclusivamente route, credenziali e sourceId della sorgente configurata; una sorgente non può essere risolta sul binding di un’altra.
Un payload non conforme viene respinto con errore standard.
Una classificazione diversa da OPEN/ANONYMOUS viene respinta nel profilo iniziale.
Una stessa Idempotency-Key non produce due elaborazioni.
Tutte le chiamate generano o propagano un correlation ID.
Nessuna sorgente esterna può raggiungere direttamente Adapter o ETL.
WFS GetCapabilities, DescribeFeatureType e GetFeature funzionano tramite Gateway.
Il risultato WFS può essere convertito nel formato geografico canonico.
WMS GetCapabilities, GetMap e GetFeatureInfo funzionano tramite Gateway quando supportati.
Il rate limit viene applicato per client e route.
Una sorgente esterna indisponibile produce un errore standard 502/504.
Le configurazioni sono riproducibili dal repository.
Un bootstrap interrotto può riprendere da checkpoint senza duplicare record già processati.
Il watermark/change token viene avanzato solo a completamento coerente del batch o checkpoint previsto.
Il passaggio FULL_SNAPSHOT -> catch-up delta -> INCREMENTAL non richiede modifiche ai verticali.
Una dashboard può ricevere aggiornamenti live tramite un binding governato senza accedere direttamente alla UDP.
31.1 Collaudi capability e predisposizione MCP
Ogni route consumer-facing è associata a un capabilityId valido e versionato.
Una capability con mcp.toolEligible=false non può essere pubblicata dal futuro MCP Server.
La stessa capability può essere risolta su binding REST e OGC senza cambiare capabilityId.
La disattivazione o deprecazione di un binding non modifica l’identità logica della capability.
Gli scope IAM dichiarati nel manifest sono applicati dal Gateway indipendentemente dal tipo di consumer.
Non esiste alcun binding MCP diretto verso UDP, Data Lake o sistemi verticali.
Una route attiva è sempre risolvibile a sourceId, capabilityId e backendBinding validi.
La disabilitazione del Source Manifest impedisce nuove invocazioni senza cancellare storico e audit.
Il Gateway consegna al Connector ingestionId, correlationId, sourceId, dataset e schemaVersion.
La stessa richiesta può essere tracciata dal Gateway al run ETL e al lineage registrato nella UDP.
Nessun client esterno può raggiungere direttamente Connector Framework, ETL o UDP.
Un servizio dati UDP può essere sostituito o riallocato modificando il binding interno senza cambiare capabilityId o contratto esterno.
Un errore ETL o una quarantena sono esposti tramite status API standard e non tramite endpoint interni.

32. Decisioni progettuali della prima release
JSON è il formato canonico dei dati amministrativi OUF.
XML è supportato esclusivamente tramite Adapter di compatibilità.
GeoJSON/JSON-FG è il formato canonico per feature geografiche normalizzate.
WFS viene supportato come protocollo sorgente.
Per nuove esposizioni OUF viene preferito OGC API - Features.
WMS viene trattato principalmente come servizio cartografico proxy, non come dataset da riversare sistematicamente nel Data Lake.
Tutte le comunicazioni con sistemi esterni attraversano il Gateway.
Il Gateway dispone logicamente di un profilo northbound e southbound; per SUAP/SUO/SUE il southbound PULL è il percorso di acquisizione prevalente.
ETL, Semantic Enrichment e Object Resolution rimangono esterni al Gateway.
Il profilo iniziale ammette esclusivamente dati OPEN o ANONYMOUS.
Le policy restano estendibili a futuri dataset personali o soggetti a restrizioni.
API, route, policy, schema e source manifest sono versionati e gestiti come codice.
Ogni endpoint consumer-facing deve essere associato a una capability registrata.
Capability e binding tecnico sono entità distinte: REST, OGC e MCP possono riferirsi alla stessa capability.
Il Capability Manifest è versionato e gestito come codice.
L’esposizione MCP è opt-in e richiede mcp.toolEligible=true.
Le capability di ingestion sono interne e non MCP-exposed per default.
La fruizione può combinare REST/OGC con SSE/WebSocket/event subscription; Event Mesh resta opzionale.
L’acquisizione dalle sorgenti autorevoli è PULL-first; gli ingress PUSH restano capability opzionali/di compatibilità.
La discriminazione e la classificazione di procedimenti, oggetti e campi sono responsabilità del Source Onboarding / Source Configuration e del Semantic Model; il Gateway applica esclusivamente la proiezione runtime approvata.
L’Extraction Profile è l’artefatto contrattuale che traduce le decisioni di onboarding in vincoli eseguibili per l’acquisizione PULL (filtri, field projection, paging, delta strategy), senza trasferire la semantica nel Gateway.
Una source instance può generare 0..N entità canoniche, preservando provenance e versione del mapping.
Tipi sorgente sconosciuti o mapping semantici mancanti non sono promossi nella UDP canonica e sono gestiti tramite stato/quarantena espliciti.

35. Riferimenti Blue Paper
La specifica mantiene la separazione prevista dal Blue Paper tra Governed Service Exposure / Urban API Gateway, API/Service Exposure, IAM, UDP e Semantic Model. Questa appendice completa la baseline logico-funzionale del Gateway definendo il primo catalogo di capability che il core OUF deve poter pubblicare o governare. Le capability elencate sono una baseline progettuale del core iniziale e possono essere estese senza modificare il principio di esposizione governata.
A.1 Regole del catalogo
Ogni capability possiede un capabilityId stabile e versionato, indipendente dall’URL fisico.
Ogni binding consumer-facing attraversa l’Urban API Gateway.
La UI, il Viewer, Analytics e il futuro MCP consumano capability; non accedono direttamente a UDP, Data Lake o sistemi verticali.
Il provider logico di ricerca e lettura è normalmente un Data Service della UDP; il Gateway applica autenticazione, autorizzazione, routing, quote, logging e versioning.
Le capability di ingestion sono interne e non sono esposte alla normale UI né a MCP, salvo decisione esplicita futura.
mcp.toolEligible è false per default e viene attivato solo per capability sicure e semanticamente stabili.

A.9 Regole comuni per le capability di ricerca
GET viene utilizzato per query semplici e filtri rappresentabili in query string; POST /search può essere introdotto per query strutturate complesse mantenendo lo stesso capabilityId o una capability esplicitamente distinta.

I filtri devono riferirsi a proprietà canoniche, non ai nomi fisici delle colonne dei verticali.
Il Gateway valida limiti, scope e parametri superficiali; la semantica della query è responsabilità del backend provider.
Le risposte devono contenere correlationId e, quando utile, informazioni di provenance e versione dello schema.
La ricerca deve essere read-only e non produrre side effect.

A.12 Criteri di accettazione del Capability Catalog
Una UI può effettuare almeno una ricerca SUAP, una ricerca SUO, una ricerca SUE e una ricerca cross-domain attraverso il Gateway.
Tutte le capability consumer-facing sono risolvibili nel Capability Registry e mappate a un provider logico.
I path esterni possono cambiare versione senza cambiare il significato del capabilityId, salvo breaking change semantico.
Le capability MCP-eligible non introducono endpoint aggiuntivi verso la UDP.
La UI non necessita di conoscere sourceId, tabelle, database, feature type WFS o URL originari.
I dati OPEN/ANONYMOUS sono gli unici risultati ammessi nel profilo iniziale.
Le capability di ingestion non compaiono nel catalogo consumer-facing standard.

T9.1 Extraction Profile runtime e separazione dalla semantica
La materializzazione tecnologica del Gateway contiene una vista compilata dell’Extraction Profile. Tale vista può includere codici sorgente, filtri, field projection e strategie incrementali, ma non contiene la motivazione/classificazione che li ha prodotti. Ontologie, vocabolari, field classification e mapping restano nei moduli di onboarding e semantica.
source-onboarding/   # modulo esterno al Gateway  sources/  procedure-types/  field-classification/  extraction-profiles/  semantic-mappings/  approvals/ouf-config/          # sola proiezione runtime Gateway  source-runtime/  extraction-runtime/  routes/  policies/
La CI del Gateway valida che ogni route PULL attiva referenzi un extractionProfileId/version pubblicato e un endpoint/credential binding risolvibile.
La validità semantica, la classificazione dei campi e l’approvazione umana sono prerequisiti di pubblicazione gestiti dal modulo di onboarding; il Gateway riceve soltanto lo stato runtime APPROVED/ACTIVE.
Nessuna HTTPRoute o PluginConfig contiene canonicalType, URI ontologiche, codici di vocabolario o classificazioni privacy come logica di routing.
La field projection compilata dall’Extraction Profile può invece essere enforced dal Gateway/Connector per impedire richieste di campi non autorizzati.

T10. Northbound: implementazione ingress
Il listener pubblico termina TLS sul load balancer o direttamente su APISIX secondo il profilo infrastrutturale. In entrambi i casi il tratto LB->APISIX deve restare TLS in produzione quando attraversa una rete condivisa. La route applica policy capability-specific.
Request -> TLS -> client/auth validation -> request-id -> rate limit ->request-validation -> route resolution -> upstream TLS -> response policy ->access log / metrics / trace
Per ingestion viene restituito 202 Accepted dopo l'accettazione tecnica da parte del Connector Framework. Il Gateway non attende il completamento ETL. Il backend deve restituire ingestionId e statusUrl conformi al contratto.
T11. Southbound: egress governato
I Connector non chiamano direttamente Internet o reti verticali. Chiamano il Service interno apisix-southbound con hostname logico e route registrata. APISIX effettua DNS resolution, TLS validation, aggiunge credenziali tecniche quando previsto e instrada soltanto verso upstream allowlisted.
connector -> https://apisix-southbound.ouf-gateway.svc/source/sue/...           -> route sourceId=sue-prod           -> credential reference from secret injection           -> https://sue.example.local/...
Nessun forward proxy generico e nessun CONNECT aperto.
Ogni destinazione ha host/SNI, porta, CA, timeout e retry dichiarati nel Source Manifest.
Retry solo per operazioni idempotenti o esplicitamente marcate safe-to-retry.
Circuit breaking e health check upstream configurati dove il protocollo lo consente.
Audit separato per northbound e southbound.
T11.1 Pattern operativo PULL-first e Source Synchronization
Il Gateway non decide quando interrogare una sorgente. La pianificazione appartiene a un componente separato Source Synchronization / Scheduler, configurato tramite Source Configuration / Connector Registry. Il Gateway fornisce il percorso southbound governato e osservabile. Questa separazione impedisce che il Gateway diventi un orchestratore di sincronizzazione.
Per ogni sourceId il profilo di sincronizzazione deve poter dichiarare almeno: initialLoadStrategy, incrementalStrategy, pollInterval, paging/cursor, watermark o change token, retry policy, checkpointing, deletion detection e concurrency limits.
Al primo avvio della sorgente la sincronizzazione esegue un bootstrap governato: FULL_SNAPSHOT -> catch-up delta -> salvataggio del watermark -> stato ACTIVE. A regime ogni ciclo PULL richiede esclusivamente le modifiche successive all’ultimo watermark confermato. Il watermark avanza solo dopo elaborazione end-to-end riuscita o checkpoint coerente.
Strategie incrementali preferite, in ordine: change token/change feed; last-modified; identificatore monotono; snapshot diff come fallback. Le sorgenti che non consentono delta efficienti devono avere frequenza e carico esplicitamente dimensionati.
I verticali non ricevono dipendenze applicative dall’OUF: nessun componente SUAP/SUO/SUE deve essere modificato per conoscere Source Sync, Gateway, Adapter o UDP.
T11.3 Southbound egress isolation e SSRF containment
Il deployment apisix-southbound DEVE operare sotto NetworkPolicy/CNI egress default-deny. Le sole destinazioni ammesse sono gli upstream censiti e approvati nel Source/Route Registry e i servizi interni OUF strettamente necessari (DNS, identity/secret endpoints, telemetry o altri endpoint esplicitamente governati). La configurazione applicativa di una route non può ampliare automaticamente il perimetro di rete.
GW-NET-01 — Ogni endpointRef risolto dal Gateway deve derivare da configurazione versionata/approvata; non è ammesso costruire un upstream da URL, host o IP arbitrario fornito dal chiamante o da payload applicativo.
GW-NET-02 — Il southbound DEVE impedire egress verso Internet generico, loopback, link-local/metadata endpoint (es. 169.254.169.254), RFC1918 non censite e qualunque destinazione non esplicitamente allowlistata. La difesa applicativa e la policy di rete sono cumulative.
GW-NET-03 — Kubernetes NetworkPolicy standard è considerata sufficiente solo quando le destinazioni possono essere espresse tramite pod/namespace selector o IP/CIDR stabili. Per FQDN con IP dinamici è richiesta una policy CNI FQDN-aware o controllo egress equivalente; l'introduzione di un egress proxy dedicato resta soggetta al Technology Economy Gate.
GW-NET-04 — Redirect HTTP/HTTPS che cambiano host o destinazione fuori allowlist devono essere rifiutati. DNS rebinding e risoluzioni multiple devono essere valutati rispetto all'allowlist effettiva prima della connessione.
GW-NET-05 — Il namespace/ServiceAccount dei workload Ingestion non ottiene egress diretto ai verticali se il contratto prevede transito obbligatorio dal southbound Gateway; un Pod compromesso non deve poter bypassare il boundary di rete.
T11.2 Fruizione sincrona e PUSH/event-driven
La scelta PULL-first riguarda l’acquisizione dalle sorgenti, non la fruizione della piattaforma. Frontend, dashboard, Viewer, Analytics e MCP possono consumare capability tramite REST/OGC e, quando il caso d’uso lo richiede, tramite canali streaming o PUSH governati. L’eventing non è un passaggio obbligatorio dell’ingestion.
Dashboard e frontend: caricamento iniziale tramite capability di lettura; aggiornamenti live tramite SSE, WebSocket o subscription/event endpoint esposto dal Gateway quando previsto.
MCP: il percorso base resta Agent Host -> MCP Server -> Gateway -> capability. Per operazioni lunghe sono ammessi progress, notifiche e streaming dei risultati, mantenendo capabilityId, scope IAM, audit e correlationId.
Event Mesh: opzionale e trasversale. Può distribuire eventi durevoli a più subscriber, ma non sostituisce REST/OGC, Workflow, persistenza autorevole o il polling delle sorgenti che non supportano eventi.
I canali realtime consumer-facing devono comunque attraversare il perimetro governato del Gateway o un binding equivalente approvato; non sono ammessi collegamenti diretti di dashboard o MCP verso UDP/Data Lake.

T14.1 etcd storage, quorum health e controlled publication
Il cluster etcd a 3 membri è un componente latency-sensitive del control plane APISIX. Ogni membro DEVE usare storage persistente SSD a bassa latenza con IOPS/throughput prevedibili e senza noisy-neighbour incompatibile con gli SLO del cluster. Una latenza elevata di fsync/commit può aumentare election churn, ritardare i commit Raft e rendere temporaneamente indisponibile il control plane; i timeout Raft non devono essere usati per mascherare storage patologicamente lento.
GW-ETCD-01 — Sono monitorati almeno WAL fsync latency, backend commit latency, leader changes/election rate, pending proposals, DB size/quota, compaction/defragmentation state e APISIX configuration propagation latency.
GW-ETCD-02 — La pubblicazione massiva di route/plugin non scrive direttamente da Onboarding a etcd. Il flusso è: PublishedConfigurationBundle -> Gateway configuration publication -> validate/compile/diff -> controlled APISIX update -> etcd.
GW-ETCD-03 — Il publication worker DEVE applicare batching/coalescing, concurrency limit e backpressure. Modifiche multiple allo stesso oggetto di configurazione possono essere consolidate prima della write; non sono ammessi burst incontrollati di write derivati da una singola sessione di onboarding.
GW-ETCD-04 — Se etcd/control plane è degradato, nuove configurazioni non diventano ACTIVE finché publication e verifica non completano con successo. Il data plane DEVE continuare, per quanto supportato dalla versione APISIX adottata, a servire la last-known-good configuration già caricata.
GW-ETCD-05 — Snapshot, compaction, defragmentation e restore sono operazioni governate. Una procedura di manutenzione che può impattare quorum o latenza viene eseguita member-by-member con health gate e runbook.
GW-ETCD-06 — Election timeout/heartbeat interval sono calibrati su RTT e latenza storage misurati. Aumentarli indiscriminatamente non è una remediation accettabile per WAL fsync p99 fuori soglia.

Da piattaforma vuota, Source Sync completa FULL_SNAPSHOT e catch-up delta di una sorgente mock attraverso APISIX southbound. I parametri di coerenza snapshot/delta previsti dalla Source API sono propagati senza alterazioni e nessuna modifica avvenuta durante lo snapshot viene persa.
TECH-22 - Watermark e resume
Un’interruzione durante la sincronizzazione riprende dal checkpoint previsto, può rileggere in sicurezza la stessa finestra incrementale e non avanza il watermark oltre l’ultimo punto coerente. Il Gateway non presume exactly-once.
TECH-23 - Pull isolation
I workload di sincronizzazione possono raggiungere una sorgente esterna soltanto attraverso la route southbound associata al relativo sourceId; l’egress diretto è bloccato da NetworkPolicy.
TECH-24 — Extraction Profile enforcement: il Gateway/Connector compone la richiesta PULL usando esclusivamente filtri, field projection, paging e delta strategy pubblicati nel profilo runtime; la Source API restituisce solo i campi richiesti e il Gateway non esegue filtraggio semantico sul payload di risposta.
Una capability realtime di test eroga aggiornamenti tramite SSE o WebSocket attraverso il perimetro governato; la UI non dispone di accesso diretto a UDP/Data Lake. Un eventuale Event Mesh non è richiesto per il superamento del test.
TECH-25 - Snapshot/delta continuity
Una sorgente mock viene modificata durante il bootstrap. Il flusso FULL_SNAPSHOT + catch-up, attraversando il Gateway southbound, acquisisce anche la modifica concorrente senza buchi tra snapshot e delta.
TECH-26 - Exit-scope passthrough
Un record già acquisito come eleggibile viene successivamente modificato in uno stato non più compreso negli eligibleStates. La Source API rende osservabile la variazione e il Gateway la inoltra al Connector senza sopprimerla sulla base del nuovo stato.

T29.2 Query Complexity Governor: separazione da rate limiting
Rate limiting, request size, connection limits e timeout del Gateway non sostituiscono il Query Complexity Governor UDP. Il Gateway non stima depth, fan-out, costo PostGIS, cardinalità o query plan e non mantiene il correlation/session budget. Se il backend rifiuta un workload per budget, il Gateway propaga Problem Details, codice OUF e Retry-After quando previsto, senza trasformare automaticamente la richiesta in un'altra capability o eseguire retry non richiesti.
GW-QGOV-01 — Un ALLOW al Gateway non implica ammissibilità del workload nel Governor.
GW-QGOV-02 — QUERY_CAPABILITY_MISMATCH, TOOL_SELECTION_STALLED e QUERY_REQUIRES_ANALYTICAL_CAPABILITY sono errori applicativi/backend; il Gateway li propaga senza reinterpretarli.
GW-QGOV-03 — Retry automatici di route non devono moltiplicare una richiesta rifiutata per budget o capability mismatch.
T29.3 Durable ACK e semantica HTTP
HTTP 202 Accepted del Gateway certifica esclusivamente l'accettazione tecnica della richiesta al boundary previsto dal contratto. Non costituisce Durable ACK dell'Ingestion Runtime. Il Durable ACK è emesso dal downstream quando payload/reference e recovery metadata sono persistiti in modo durevole secondo il contratto UDP v1.2; il Gateway non lo sintetizza e non autorizza l'avanzamento del committed watermark.
GW-ACK-01 — Test E2E deve dimostrare che un 202 del Gateway seguito da failure prima della persistenza downstream non produce avanzamento del watermark e che il replay conserva lo stesso handoffId/idempotency semantics.
T29.4 Schema Surveillance preflight passthrough
Le route di discovery/preflight devono preservare senza reinterpretazione gli indicatori tecnici disponibili dalla sorgente: schemaVersion, schemaFingerprint, catalogVersion, ETag/Last-Modified, collection/layer version e altri token contrattuali. Il Gateway può applicare timeout, auth, rate limit e payload controls, ma non classifica il drift e non modifica il bundle ACTIVE.
GW-SCHEMA-01 — Se fingerprint/ETag è invariato, il Gateway non forza full schema discovery. Se varia, rende raggiungibile la discovery tecnica governata; COMPATIBLE/BREAKING/RE_ONBOARDING_REQUIRED restano decisioni Runtime/Onboarding.

T33.16 Definition of Done v1.3 — handoff allo sviluppo/deployment
La baseline tecnologica corrente è unica e autoritativa; nessuna decisione già assunta resta descritta come futura nel perimetro implementativo.
Il repository contiene capability/source/extraction/route/policy manifests, schema macchina, environment overlays e generated-config evidence.
Git commit -> validation -> deterministic compile -> staged verify -> activation -> PublicationManifest è testato e rollbackabile.
Northbound/southbound NetworkPolicy, endpoint allowlist, SSRF hardening, OIDC/mTLS e secretRef passano negative-path security test.
etcd quorum, slow-storage behavior, snapshot/restore e post-restore convergence sono provati su infrastruttura rappresentativa.
Compatibility N/N+1 per manifest/config/controller/runtime è dichiarata e testata durante rolling upgrade.
Graceful drain, PDB/HPA, realtime connections, upload streaming e source timeouts sono coperti dal performance/fault profile.
Dashboard, alerts, runbook, compatibility manifest, SBOM/provenance e test evidence fanno parte del supplier handoff.
Il cross-module activation gate impedisce route ACTIVE con capability, source runtime, extraction profile, authorization binding o backend reference incoerenti.
Non restano TBD implementativi interni al Gateway. Gli unici binding valorizzabili a integration/deployment time sono esterni e già modellati: scenario IAM/M2M A/B/C, issuer/audience/trust, DNS/VIP/LB/firewall, PKI/secret manager endpoints, source/backend endpointRef e storage-class/DR parameters.
Stato reale della specifica v1.3: development-ready per implementazione, configurazione, integrazione e collaudo dell’Urban API Gateway. La revisione non introduce nuove responsabilità applicative nel Gateway: routing, boundary security, configuration publication e network governance restano il suo perimetro; semantica, fine-grained authorization, query governance, ingestion durability e trasformazione dati restano ai rispettivi owner.

34.2 Mediation requirements
Le query MCP operational-awareness verso Ingestion/Onboarding/altri owner passano dal Gateway con identity propagation e authorization context verificabile.
Il Gateway non può trasformare una failure di un modulo non raggiungibile in “nessun incidente”: deve restituire MODULE_UNAVAILABLE/PARTIAL con correlationId.

34.3 Telemetry versus user-facing incident
Metriche e log rimangono high-cardinality telemetry; gli OperationalEvent sono low-cardinality semantic transitions.
Il Gateway deve applicare debounce/dedup per evitare un incidente per ogni singolo 5xx/timeout.
Una recovery deve aggiornare/chiudere l’incidente correlato anziché generare solo un evento isolato.

35. Channel-neutral Operational Awareness mediation
Normative correction v1.5. Urban API Gateway is the common mediation boundary for human-facing Operational Awareness capabilities regardless of presentation channel. MCP, a future UI, CLI and approved automation clients consume the same governed capability identities; channel-specific adapters MUST NOT create alternate owner paths.
35.1 MCP-owned capability routing
Gateway MUST register MCP Server as a normal backend owner for ouf.system.status through a private MCP owner API endpoint.
The backend route MUST target /api/internal/v1/mcp/operations/status (or versioned equivalent) and MUST NOT target the MCP protocol endpoint /mcp.
Allowed caller identities/scopes are governed by Authorization and route policy, not hard-coded to chatbot semantics. MCP Server is one allowed caller, not the capability owner/exposure monopoly.
Gateway MUST propagate correlation and verified identity/authorization context to the MCP owner endpoint.
NetworkPolicy and workload identity MUST prevent external/direct calls to the owner endpoint; the Gateway remains the public/internal northbound mediation boundary.
35.2 Cross-channel acceptance criteria OA-GW-CN
OA-GW-CN-01: compiled Gateway config contains capability and route binding for ouf.system.status owned by MCP.
OA-GW-CN-02: MCP caller and a synthetic approved non-MCP caller resolve to the same capability/backend binding under different Authorization decisions.
OA-GW-CN-03: no route backend for ouf.system.status points to /mcp.
OA-GW-CN-04: unauthorized caller receives denial and cannot infer protected status.
OA-GW-CN-05: owner endpoint is not exposed as a standalone public route.
