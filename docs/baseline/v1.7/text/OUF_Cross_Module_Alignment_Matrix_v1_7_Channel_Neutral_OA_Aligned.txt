6.1 Canonical lifecycle and severity
lifecycleState = OPEN | RECOVERING | RESOLVED; severity = INFO | WARNING | ERROR | CRITICAL
Operational events are durable semantic transitions, not a mirror of logs/metrics.
dedupKey + incidentId aggregate equivalent retry/fault events; recovery closes the same incident when causally equivalent.
Each event carries module ownership, timestamps, correlation context, visibility class, safe impact summary and evidence references.
Live notification is optional; persistent catch-up is mandatory.
6.2 Canonical chatbot scenarios
OUF-OA-001 — User reconnects after scheduled ingestion transient failure that self-recovered: summary reports RESOLVED incident, duration, retry count and no action required.
OUF-OA-002 — User reconnects after terminal scheduled ingestion failure: OPEN incident reports source/job, safe error code, last attempt and action required.
OUF-OA-003 — Gateway cannot reach one producer while other modules are healthy: system.status is PARTIAL/UNKNOWN for the missing producer, not global HEALTHY.
OUF-OA-004 — Security-sensitive fault exists but actor lacks permission: response preserves redaction/authorization semantics without disclosing protected detail.
OUF-OA-005 — Repeated equivalent timeout generates one incident timeline rather than notification storm.
OUF-OA-006 — Lost live notification followed by reconnect still returns the persisted incident through summary/history.
6.3 Release gates
Each producer PET has persistent operational-event requirements and retention.
MCP PET exposes bounded operational capabilities and preserves partial/unknown semantics.
Gateway routes and authorizes operational queries without new network bypasses.

Pairwise tests cover Ingestion↔Gateway↔MCP and denial/redaction cases.
Full-path acceptance includes offline fault → persisted incident → later chatbot catch-up.
7. Channel-neutral human-facing capability alignment
This section is normative for all work after Matrix v1.7. It corrects an MCP-centric ambiguity introduced during the first Operational Awareness implementation slice.
Invariant
Alignment rule
Capability identity
Human-facing OUF functionality is defined as a channel-neutral capability, not as an MCP-only tool.
Common mediation
Urban API Gateway mediates approved human-facing capability execution for MCP, UI, CLI and automation channels.
MCP role
MCP provides governed conversational discovery/invocation; it does not own exclusive application access.
Owner role
Each physical module exposes a private owner API for its capabilities, including MCP-owned capabilities.
No recursion
Gateway -> MCP owner API is permitted; Gateway -> /mcp for MCP-owned capability execution is forbidden.
Security equivalence
Authorization, tenant isolation, redaction, audit and evidence semantics do not weaken or change by presentation channel.
Network boundary
Private owner APIs are reachable only from approved Gateway/control-plane identities according to NetworkPolicy/trust policy.
7.1 Corrected ouf.system.status topology
Chatbot path: Human -> chatbot/MCP client -> MCP protocol/tool projection -> Urban API Gateway -> MCP private owner API -> MCP authoritative datastore projection.
Future UI path: Human -> UI -> Urban API Gateway -> MCP private owner API -> MCP authoritative datastore projection.
The two paths share the same capability identity and backend owner contract. Their authentication mechanism may differ, but Authorization and information-disclosure semantics remain governed and comparable.
