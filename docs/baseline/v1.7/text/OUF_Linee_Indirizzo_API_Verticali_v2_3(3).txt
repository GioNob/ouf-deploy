OPEN URBAN FRAMEWORK (OUF) — BLUE PAPER
Documento di indirizzo per la progettazione delle Source API dei verticali OUF, con profili applicativi SUAP, SUO e SUE
Source API read-only, PULL-first, incrementali, osservabili e semanticamente neutre
Versione 2.3 — Settembre 2026
Documento di indirizzo tecnico-funzionale rivolto ai fornitori, gestori applicativi e responsabili di integrazione di qualunque sistema verticale destinato a essere acquisito dall'Open Urban Framework. SUAP, SUO e SUE costituiscono i profili applicativi iniziali e gli esempi di riferimento, ma i requisiti core sono generali e riusabili per verticali amministrativi, gestionali, territoriali/GIS, mobilità, ambiente, sensoristica/IoT e ulteriori domini urbani. Lo standard definisce come una sorgente deve esporre dati e metadati nativi affinché OUF possa acquisirli in PULL, governarli tramite Onboarding e trasformarli nel proprio modello informativo senza imporre semantica OUF alla sorgente.
Allineamento v2.3. La presente revisione recepisce le Executive Freeze OUF: Data Lake / UDP / Urban Object Registry v1.2, Ingestion Runtime v1.2, Source Onboarding & Configuration v1.3, Authorization & Access Control v1.3, Urban API Gateway v1.2 e Semantic Model / Registry v1.2. Rafforza Preflight Contract Check, schema surveillance, source-object identity, temporal mapping, change representation, minimizzazione, M2M, southbound governance, GIS/feature exposure e compatibilità con sorgenti ad alta frequenza, mantenendo invariati i principi read-only, PULL-first e semanticamente neutri.
Principio guida
Il verticale non è un componente dell’OUF e non deve conoscerne modello canonico, ontologie, vocabolari, classificazioni o capability. Deve esporre in modo affidabile i propri dati nativi, i propri schemi e le variazioni incrementali. L’interpretazione del dato appartiene alla piattaforma Smart City.
1. Scopo e decisione architetturale
Il presente indirizzo definisce il profilo standard OUF Source API, applicabile a qualunque verticale o sistema sorgente che debba rendere dati disponibili all'OUF. SUAP, SUO e SUE sono i primi profili applicativi, non il limite dello standard. Il pattern prevalente è PULL: la piattaforma determina quando interrogare la sorgente, quale intervallo/checkpoint usare, quali tipi o collezioni acquisire e quali campi nativi richiedere. Il verticale resta passivo rispetto a OUF e non deve essere obbligato a inviare webhook, messaggi o notifiche verso la piattaforma.
L'obiettivo operativo è supportare bootstrap, catch-up e sincronizzazione incrementale del perimetro configurato. Per SUAP/SUE/SUO il perimetro iniziale può essere costituito dalle istanze concluse secondo stati nativi approvati; per altri verticali può riguardare record attivi, osservazioni temporali, feature geografiche, asset o qualunque insieme definito dall'Extraction Profile. Lo standard richiede continuità e ripetibilità, non una specifica semantica di dominio.
Separazione delle responsabilità
La Source API espone dati e metadati tecnici nativi. Il modulo Source Onboarding / Source Configuration della Smart City costruisce l’Extraction Profile e i mapping. Il Gateway applica solo la proiezione tecnica approvata. Adapter, ETL e Semantic Model trasformano e interpretano i dati dopo l’acquisizione.

3. Onboarding come premessa all’acquisizione
Prima di attivare una sorgente, la piattaforma esegue una procedura di onboarding separata dal Gateway. In tale procedura vengono censiti la fonte, le tipologie/collezioni native, gli oggetti o record ricavabili, i campi nativi e i relativi schemi. Su questa base l’operatore associa classificazioni, ontologie, vocabolari controllati, regole di trasformazione e politiche di acquisizione.
Il verticale deve quindi fornire abbastanza metadati tecnici per rendere possibile l’onboarding, senza incorporare semantica OUF. In particolare devono essere disponibili codici stabili, etichette native, schema dei campi, tipi dato, cardinalità, codifiche native e versioni.
Fonte SUAP  └─ Procedimento nativo: PROC_047      ├─ schema/versione      ├─ campi nativi      ├─ stati nativi      └─ sample tecnico opzionaleOnboarding OUF  └─ classifica i campi  └─ decide INCLUDE / EXCLUDE  └─ associa ontologie e vocabolari  └─ definisce mapping e regole  └─ genera Extraction Profile APPROVED/ACTIVE
AI-ready e Human-in-the-loopIl modulo Source Onboarding & Configuration può essere assistito da AI Agent tramite MCP per proporre classificazioni, mapping e analisi del drift. Il contratto del verticale non cambia: l’AI opera sulle capability governate della piattaforma e ogni modifica autoritativa resta soggetta a decisione umana verificata.
4. Extraction Profile: contratto di minimizzazione tecnica
L’Extraction Profile è un artefatto della piattaforma, non del verticale. Deriva dall’onboarding e traduce decisioni di governance e semantica in istruzioni tecniche di acquisizione. Il verticale non riceve la motivazione semantica delle scelte; riceve esclusivamente parametri tecnici come tipi, stati, campi e finestra incrementale.

La Source API DEVE poter evitare il transito di campi non inclusi nel profilo quando il modello nativo contiene dati non acquisibili. 5. Contratto minimo della Source API
Le API possono differire internamente tra i verticali, ma devono offrire un nucleo comune di capacità. SUAP, SUO e SUE rappresentano i primi profili applicativi dello standard; i verticali futuri devono conformarsi allo stesso nucleo, salvo estensioni motivate dal dominio. Il prefisso dei path è indicativo; ciò che è vincolante è il comportamento.
Nel presente documento: DEVE identifica un requisito di conformità; DOVREBBE una raccomandazione forte; PUÒ una caratteristica opzionale. Lo standard prescrive le garanzie del contratto, non la tecnologia interna con cui il verticale le realizza.

6.1 Preflight Contract Check: contratto leggero obbligatorio
Prima di ogni run schedulata OUF esegue un Preflight Contract Check leggero. La Source API DEVE consentire di verificare esistenza/attività del type/collection, schemaVersion o schemaFingerprint e, quando disponibili, catalogVersion, ETag o Last-Modified senza obbligare a scaricare lo schema completo. Se il contratto è invariato, OUF procede all'acquisizione; la full discovery è richiesta solo per scope cambiati.

7. Modello dei dati restituiti
La piattaforma deve poter distinguere con certezza ogni istanza, la sua tipologia e la versione dello schema usato per interpretarla. Non è richiesto che tutti i procedimenti condividano un unico schema. Al contrario, le differenze native devono restare osservabili. Ogni record deve dichiarare schemaId/schemaVersion o un riferimento tecnico equivalente: una finestra snapshot/delta può contenere record di versioni differenti solo se ciascun elemento resta auto-descrivibile e la transizione è rilevabile senza ambiguità.

7.1 Identità source-object e sotto-entità
La chiave di provenienza OUF è (sourceId, typeCode, sourceObjectId). sourceObjectId identifica il singolo record/feature/asset/observazione nel relativo typeCode e NON il dataset nel suo complesso. Se un payload contiene sotto-entità che devono essere sincronizzabili o referenziabili autonomamente, il verticale DOVREBBE esporre identificatori stabili anche per esse. L'OUF decide se una o più istanze native generano zero, uno o più Candidate Urban Object.

8. Perimetro di acquisizione e stati eleggibili
La Source API deve permettere a OUF di esprimere il perimetro tecnico di estrazione tramite tipi/collezioni, stati, date, partizioni o filtri nativi documentati. Nei profili SUAP/SUE/SUO il bootstrap e il delta ordinario possono essere limitati alle istanze che l'Onboarding classifica operativamente come concluse. Per verticali generici il perimetro può invece includere record attivi, feature correnti, asset o osservazioni. Il verticale espone valori nativi; OUF decide quali siano eleggibili.
Verticale espone stati nativi:  CHIUSA_POS  CHIUSA_NEG  ARCHIVIATA  IN_CORSO  SOSPESAOnboarding configura:  eligibleStates = [CHIUSA_POS, CHIUSA_NEG, ARCHIVIATA]Runtime PULL:  GET /procedures?status=CHIUSA_POS,CHIUSA_NEG,ARCHIVIATA&...
Se il verticale possiede già un attributo tecnico affidabile come terminal=true o finalState=true, esso può essere utilizzato, ma non deve sostituire la disponibilità dei codici di stato nativi necessari all’onboarding e all’audit.
9. Bootstrap iniziale
Alla prima attivazione della sorgente la piattaforma deve poter acquisire tutte le istanze del perimetro definito dall'Extraction Profile. Nei profili SUAP/SUE/SUO il perimetro può coincidere con le istanze concluse; per verticali generici può comprendere record attivi, asset, feature o osservazioni. Il bootstrap deve essere ripetibile, paginato, restartable e compatibile con il fatto che il verticale continui a modificarsi durante l'estrazione.
Fase
Comportamento richiesto
1. Punto di coerenza
Prima dello snapshot la piattaforma acquisisce T0, un high-water mark, snapshot point o meccanismo equivalente. La Source API DEVE garantire che snapshot e successivo catch-up possano essere concatenati senza perdita di modifiche avvenute durante l’estrazione.
2. Snapshot
Scarica tutte le istanze del perimetro secondo tipi/collezioni, filtri nativi e field projection del profilo.
3. Checkpoint
Conserva cursor/pagina e progress per permettere il resume.
4. Catch-up
Terminato lo snapshot, richiede tutte le variazioni successive a T0.
5. Validazione
Confronta conteggi, errori e quarantene.
6. Attivazione
Solo dopo il catch-up salva il watermark operativo e passa al delta ordinario.
Garanzia di continuità runtime: lo standard non impone asOf, snapshotId, CDC o altra tecnologia specifica. Impone però che esista almeno un meccanismo documentato che renda completa la sequenza snapshot → catch-up → delta, senza buchi tra i dati letti nello snapshot e le modifiche recuperate successivamente.
FULL SNAPSHOT      ↓catch-up da T0      ↓VALIDATION      ↓watermark confermato      ↓INCREMENTAL SYNC
10. Sincronizzazione incrementale
A regime la piattaforma deve chiedere esclusivamente ciò che è nuovo o modificato dopo l’ultimo checkpoint confermato. L’API deve supportare una strategia di delta deterministica e documentata.

Il token o checkpoint successivo deve diventare operativo solo dopo che la piattaforma ha completato con successo l’elaborazione della finestra corrispondente. In caso di errore la stessa finestra DEVE poter essere riletta senza perdita di dati. La Source API non deve promettere exactly-once: eventuali riletture o duplicazioni tecniche devono essere riconoscibili tramite identificativo stabile, revisione e/o checkpoint e gestibili idempotentemente dalla piattaforma.
Visibilità dell’uscita dal perimetro: una variazione di un record già precedentemente estraibile DEVE restare osservabile nel flusso incrementale anche quando la modifica lo rende non più conforme ai filtri correnti dell’Extraction Profile (ad esempio una pratica conclusa che viene riaperta). Il verticale è libero di rappresentare tale variazione come aggiornamento, tombstone o meccanismo equivalente, purché la piattaforma possa rilevarla.
10.1 ChangeRepresentationProfile e contratti delta
Profilo OUF
Capacità sorgente richiesta
Regola

Una Source API NON è obbligata a implementare DELTA_PATCH o PROPERTY_EVENTS. FULL_SNAPSHOT nel change feed è conforme se il delta identifica in modo affidabile quali record sono cambiati.
Se DELTA_PATCH è supportato, ogni operazione deve identificare sourceObjectId, base revision/token/hash, operation (SET/REMOVE o equivalente), sourcePath stabile e nuova revisione/sequence. Il verticale non conosce targetProperty OUF.
Se PROPERTY_EVENTS è supportato, il contratto deve dichiarare ordering scope, eventId/sequence, deduplication key, retention e procedura di catch-up dopo consumer downtime.
Un cambio della semantica di patch path, event ordering o base reference è una breaking contract change anche se il JSON resta sintatticamente valido.
11. Cancellazioni, rettifiche e cambi di perimetro
Una replica incrementale è corretta solo se rende osservabili anche variazioni che non corrispondono a un semplice aggiornamento. Il verticale deve rappresentare cancellazioni logiche o fisiche, annullamenti/rettifiche e, quando applicabile, transizioni che fanno entrare o uscire un record dal perimetro configurato. Nei profili amministrativi ciò include anche riaperture di pratiche precedentemente concluse.

12. Field projection e privacy by minimization

Il Gateway/Connector applica l’Extraction Profile costruendo la richiesta con i filtri e la proiezione tecnica approvati; è la Source API del verticale che DEVE eseguire materialmente la projection prima di produrre la risposta, così che i campi esclusi non attraversino il confine della sorgente. Se un campo necessario al controllo tecnico del record non è incluso nel payload data, può essere esposto come metadato tecnico comune purché documentato e ammesso.
13. Paging, cursor, ordinamento e coerenza
Il cursor DOVREBBE essere opaco e stabile per la durata della lettura.
L’ordinamento DEVE essere deterministico e documentato.
La pagina successiva non deve perdere o duplicare elementi a causa di inserimenti concorrenti.
L’API DOVREBBE supportare snapshotAt/asOf, high-water mark o meccanismo equivalente; in ogni caso DEVE essere garantita la continuità tra snapshot e successivo delta come definita nella sezione 9.
pageSize massimo e default DEVONO essere dichiarati.
13.1 Concorrenza delle letture e isolamento dei flussi
La Source API deve essere progettata assumendo che OUF possa eseguire più letture concorrenti: discovery tecnico, schema surveillance, snapshot, delta, dettaglio diagnostico e verifiche di health possono sovrapporsi. La concorrenza non deve alterare la coerenza dei cursor, la continuità snapshot→delta o la visibilità delle modifiche.
Il verticale DEVE documentare rate limit e limiti di concorrenza per client/route.
Cursor e snapshot context non devono dipendere da una sessione HTTP esclusiva o da un singolo consumer.
Richieste di discovery/schema check non devono invalidare una scansione dati in corso.
Se il verticale applica throttling, DEVE usare 429/503 e Retry-After senza introdurre perdita di stato.
Il client deve poter ripetere una pagina o una finestra senza effetti collaterali.

Queste codifiche rimangono sorgente e saranno eventualmente mappate a vocabolari controllati OUF durante onboarding.

14.1 Schema Surveillance e rilevazione del drift
OUF esegue schema surveillance in modalità PULL confrontando il contratto tecnico ACTIVE con il catalogo/schema osservato. Il verticale non deve inviare webhook né conoscere lo stato interno OUF, ma deve rendere rilevabili anche le variazioni compatibili, inclusa l’aggiunta di un campo non richiesto dall’attuale fieldProjection.
OUF Schema Surveillance        | periodic PULL        vSource API discovery / catalog-version        | schemaVersion + schemaFingerprint        vCOMPARE with ACTIVE SourceSchema        |        +--> compatible change  -> review / optional re-onboarding        +--> breaking change    -> RuntimeIssue / RE_ONBOARDING_REQUIRED
La classificazione operativa del drift appartiene a OUF. Il verticale deve soltanto rendere il cambiamento osservabile e continuare a descrivere in modo non ambiguo la versione applicabile. Una nuova schemaVersion non viene automaticamente attivata in OUF: può richiedere una nuova OnboardingVersion e un nuovo PublishedConfigurationBundle.
14.2 Compatibility window e cambio contratto governato
Per modifiche breaking, il verticale DOVREBBE mantenere per un periodo dichiarato il contratto precedente o un meccanismo equivalente che consenta la transizione governata. Non è richiesto conservare indefinitamente le versioni storiche: tale responsabilità di audit/replay appartiene alla piattaforma OUF. È invece vietata, salvo emergenza documentata, la sostituzione silenziosa e immediata di un contratto ACTIVE con uno incompatibile.
schema 3.2 ACTIVE      |      +--> schema 4.0 AVAILABLE (BREAKING)              |              v      OUF detects drift -> new onboarding -> new bundle ACTIVE              |              v      runtime switches on a new synchronization cycle
14.3 Isolamento dello scope su schema drift
Quando catalogo e API sono strutturati per type/collection indipendenti, una modifica breaking DEVE essere identificabile sullo scope minimo interessato. È fortemente raccomandato che schema/version/fingerprint siano per type/collection, così OUF possa sospendere o ri-onboardare solo lo scope incompatibile senza fermare l'intero verticale.

31. Cross-Module Alignment Freeze v2.3 — dichiarazione finale
La v2.3 allinea le linee di indirizzo alle Executive Freeze dei moduli OUF correnti e rende il profilo Source API riusabile per verticali generici. Restano normativi: sorgente semanticamente neutra; PULL-first; discovery/versioning; Preflight Contract Check; bootstrap/catch-up/delta; field projection alla sorgente; sourceObjectId stabile; temporalità native; schema surveillance scoped; M2M service identity; southbound Gateway; errori machine-readable; concurrency e backpressure; FULL_SNAPSHOT come baseline universale e profili delta avanzati solo quando tecnicamente supportati. SUAP/SUE/SUO specializzano il perimetro amministrativo senza vincolare i futuri verticali.
